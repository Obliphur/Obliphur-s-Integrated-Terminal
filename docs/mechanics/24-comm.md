### 24.22 共同阅读

沟通页聊天栏上方的 📚 图标入口（阅读）弹出「自己阅读 / 发起 coread」选择，❓ 帮助同步说明。自己阅读直接使用书库与阅读器，不启动人设会话、不显示网页聊天，也不锁定原沟通页；用户选择发起共读后，`📚 共读` 作为附件加入待发送内容，随下一条消息发送；人设用 `oit_reply.answer="yes"` 明确同意后才打开共读室。拒绝、未明确表态、沉默、错误或五分钟未回复均作废，清空聊天或切换人设会取消请求。Claudia 主动申请仍须用户接受。share data 与共读附件分别显示为 `🙈 share data`、`📚 共读`，演奏评判显示为 `🎼 演奏评判`；附件标签放在工具图标下方的第二行，发出的消息也将附件说明放在正文首行。Windows 启动服务时显示准备 / 安装进度与失败原因，成功后通过本机回环地址打开浏览器；配对安卓沿局域网地址访问同一书库，入口与模式选择一致。共读会话在选书和阅读阶段均可从网页聊天浮窗讨论书目；选书期间本机刷新书架以显示新增书籍。`oit_reading_acquire` 仅接受 Project Gutenberg 官方书目 URL，限制文件大小，校验 HTTPS 来源、电子书编号、UTF-8、书名及全文首尾标记，并在书籍正文保留来源、SHA-256 和校验说明；不支持或校验失败的来源不入库，完整性判断仅对应来源版本，不作其他地区版权结论。coread 请求入口及待发送附件均显示 📚 图标。阅读服务部署在本地 Windows，不部署外部服务器。组件源码位于 `third_party/coread/`，保留上游 MIT 许可和 OIT 集成说明。

Claudia 可通过 `oit_reading_offer` 申请共读。是否明确表示当前没有其他事情、是否直接邀请共读，由模型结合完整上下文判断；程序不使用正则或关键词判断含义，只核验工具提供的引文确实出自近 30 分钟内的用户消息。主动申请必须依据用户明确表示当前空闲的原话。申请与对应邀请正文一起生效，用户在沟通栏接受后才打开阅读室；邀请显示后 5 分钟未处理失效，取消或未展示的回复不产生可接受申请。

阅读网页提供可展开聊天框，沿用 OIT 当前人设、聊天记录和模型配置。共读设置中的 AI 名称固定为当前人设名，不可编辑。发送时附带当前书籍、页码和可见页作为本轮上下文；模型另可使用 `oit_reading_books`、`oit_reading_page` 和 `oit_reading_comment` 查询本机书籍、翻阅和批注。会话绑定开始时的人设及随机会话编号，期间原 OIT 聊天入口锁定，避免多入口串线。切换人设、结束阅读或阅读网页心跳中断后恢复原聊天。

每次共读从会话开始累计与人设日程中循环专注、重要活动和睡眠的实际重叠时间，三类合计最多 10 分钟；同一时段重叠只计一次，跨午夜继续累计。达到上限程序自动结束，不由模型自行计时。Claudia 也可以调用 `oit_reading_end`，结束说明实际显示后结束本次会话；用户可随时从网页或 OIT 结束。

共读服务 URL、访问密钥与邀请状态沿已有加密设备同步通道共享；书库、批注和阅读进度保存在 Windows 共读数据目录，安卓访问同一份本机书库。运行中的会话编号和活动累计只属于当前 Windows 服务，不通过普通聊天存档恢复。检查：`python checks/_coread_check.py`、`python checks/_comm_tools_check.py`、网页 `npm run check` / `npm run build` 和安卓沟通单测。

消息提示音可在设置 → 音效 → 收到信息选择内置音效、自选文件或静音（1.3），原有隐藏消息、未读和焦点设备规则不变。

和一个 AI 人设聊天. 电脑 `comm/` / `pages/comm_page.py`, 手机 `core/Comm.kt` / `ui/CommScreen.kt`, 两边逻辑一样; 聊天记录随设备同步 (24.6). 回复正文之外的 API 原始控制文本不保存到消息记录或设备同步。

### 24.1 设置 (设置 → 沟通 / 额外功能, 即时保存, 没有等待期)


- **自动获取模型列表**：模型与语音配置页打开已有配置、切换配置，或修改 API 地址 / Key 后停顿 700 毫秒时，后台自动请求模型列表，不改变当前型号。MiniMax 的 `/models` 只返回文本模型；语音页从公开的 `https://platform.minimax.io/docs/api-reference/speech-t2a-http.md` 获取 T2A 请求 schema 的 `model` 枚举，不携带 API Key，也不声称是账号权限列表。内置回退包含 speech-2.8 / 2.6 / 02 / 01 的 HD 和 Turbo。请求按配置、地址和 Key 缓存；过时结果不覆盖当前配置。页面显示获取中、成功或失败，允许重新获取；失败保留预设 / 当前型号，也可手动填写。文本模型页继续使用其服务商模型接口。

- **AI 语音**：设置 → 额外功能。默认关闭；开启后展开配置选择、配置页面入口、自动播放与播放间隔。仅支持 MiniMax 模板，可建立、改名、删除多份配置，每份独立填写模型、音色 ID、语音 API 地址与 API Key；国内地址 `https://api.minimaxi.com/v1/t2a_v2`，国际地址 `https://api.minimax.io/v1/t2a_v2`，非流式返回 MP3。按人设选择配置，不默认借用别人的配置。内置 Claudia 默认配置不可删除，仅 `Claudia.txt` 可使用；默认音色为区分大小写的 `claudia1999`，可以填写其他 voice_id 或应用合成音色；旧版误填的文件 ID `462298003509468` 自动迁移到正确默认值。API Key 由用户填写，账号须有对应音色权限。服务端失败显示错误码和脱敏后的原因，便于区分音色不存在、鉴权或余额问题。
- **音色合成子页面**：语音配置中的「音色合成」使用当前草稿的地址和 Key。提示词模式填写声音描述和最多 500 字的试听文本，调用同源 `/v1/voice_design`；克隆模式选择 mp3 / m4a / wav 录音（10 秒至 5 分钟、最大 20 MB），用 multipart 上传 `/v1/files/upload`，purpose 为 `voice_clone`，或直接填写已有 `file_id`，再调用 `/v1/voice_clone`。新 voice_id 可自填（8–256 位、英文字母开头、字母数字横线下划线、末尾字母数字），留空自动创建。file_id 仅作为克隆素材编号，绝不存为音色 ID。成功显示实际 voice_id；提示词模式复用返回的试听音频，克隆模式首次试听通过所选模型合成并激活音色，后续试听复用临时缓存。「使用此音色」写入父配置草稿，父页保存后生效；关闭子页停止播放并清理试听缓存。创建和上传在后台执行，页面关闭不再更新 UI；服务端已创建的音色和文件保留在 MiniMax 账号中。
- **语音生成与缓存**：开启后，AI 的正式回复一收到就后台生成（包括暂时隐藏的回复、其他人设的主动消息；同步收到的消息复用原设备传来的音频，缺失时手动播放仍可生成），不等待用户点击。系统消息、拒绝标记不生成。相同人设和消息的请求合并；成功音频立即保存在 `voice_cache/`；本机未发送的分条回复等正文发送后再同步到绑定设备，其他消息沿原流程自动同步，播放时直接复用，失败后可重试。点击 AI 消息框左下角紧贴边缘的播放图标播放；播放器成功开始后才标记已播放。切换人设、离开沟通页、沟通不可用时停止播放。清空某个人设聊天会清掉其音频与播放记录，也丢弃清空前尚未返回的生成结果；重置清除所有语音配置与音频。语音请求失败不影响文字聊天。
- **播放时段**：手动播放、自动播放和音色合成子页的试听，仅在用户状态为 `idle`（空闲）或 `break`（休息）时允许。以真实状态独立判断，不跟随开发者模式或内置 Assistant 在专注时可聊天的例外。专注、睡眠、外出及未初始化状态禁止开始播放；进入这些状态后取消播放和自动队列，播放器每 100 毫秒检查状态，音频加载 / 准备完成后也再次检查，禁止加载期间切换状态后的延迟播放。未开始播放不标记已播放。新消息仍可在后台生成并缓存，回到空闲 / 休息后可播放；恢复允许状态不会自动重启已取消的队列，重新打开沟通页按原规则选取。
- **自动播放**：默认关闭；每次打开沟通页或切换聊天对象，选取当前可见 AI 消息中从未播放过的最近 10 条，按从旧到新的顺序播放。先滚到最早一条，之后随播放定位消息；每条播放完成后等待 k 秒再播下一条，k 默认 1 秒，可设 0–60 秒。手动点语音会取消本轮队列。离页、清空、关闭语音、沟通不可用或离开允许播放的状态时取消，不播放隐藏消息。生成过但没播放过仍算未播。
- **配置帮助**：模型配置与语音配置窗口右上角均有「帮助」。语音帮助中文附 `https://platform.minimax.cn`，英文附 `https://platform.minimax.io`，逐步说明账号、Key、地址、模型与音色的填写。
- **语音同步**：`ai_voice.json` 存配置与即时开关，Key 在 Windows 用 DPAPI、Android 用 Keystore 加密；通过已有加密设备同步通道的 `comm.voice` 文档按修改时间同步，对方重新加密落盘。每轮同步快照另带 `voices` 清单，以人设名与消息 UID / 文本的 SHA-256 定位缓存；旧缓存与 `.played` 文件自动纳入，不依赖配置修改时间。已听状态取并集，任一设备成功开始播放后，其他设备也视为已听，旧的未听状态不会覆盖已听。缺失 MP3 通过已有加密文件通道后台补传并校验大小 / SHA-256，不把音频塞进文档，也不弹文件通道通知；失败下轮重试。已有音频不重复传输、不因收到文字而重新调用语音 API；生成与同步并发时保留先落盘的音频。清单仅包含仍在本机聊天记录中的 AI 消息，下载落盘前再次核对，防止清空聊天期间旧文件或播放记录复活。支持母子端双向传输与经母端中继；旧版没有清单时跳过，双方需升级后生效。
- **语音联网**：开启语音时，配置的语音 API 主机和公开型号文档主机 `platform.minimax.io` 与模型 API 一样加入过滤代理 / VPN 的接口例外；合约网络禁令仍优先。请求沿用系统代理并拒绝重定向，不把 Key 带到其他地址。

- **模型配置**: 最多 10 份命名的 API 配置 (`ai_config.json`, Key 加密保存)；已安装并登录的 Claude Code 另作为本机订阅配置出现。Claude Code 每个人设维护一个影子会话，首次用 OIT 的可见历史建立，之后只发送新增消息；OIT 仍只保存和显示干净的用户/对方正文，清空聊天会销毁该会话。型号默认由订阅客户端选择；OIT 读取 `claude --help` 判断是否支持 `--model` / `--effort`，不读取账户额度或伪造模型列表。默认 effort 为普通聊天 low、主动发起等需要判断的请求 medium；配置页可改为 auto / low / medium / high / max，旧版 CLI 不支持时自动省略参数。卸载 Claude Code 后才允许删除配置。在设置 → 模型分项新增/修改配置、选择聊天主模型、OCR、评判和数学/物理/化学教育任务模型；任务模型默认跟随聊天主模型，沟通页给每个 AI 选一份，规则页的 AI 建议使用聊天主模型。聊天图片直接交给聊天主模型；教育子代理在主模型发起 `oit_subject` 时可复用本轮图片，但不接收聊天人设和完整聊天历史。规则页的模型入口会跳到 Assistant 并预填配置请求。
- **人设**：在人设卡片选择、导入或创建人设。普通 `.txt` / `.md` 文件以文件名为角色名，正文为提示词。导入会把外部文件复制进人设文件夹。
- **人设简介与创建**：选择人设 X 后，点击“打开人设简介”查看 `X_profile.txt`。简介不进入聊天提示词或日程解析，修改简介不会触发清除聊天提示。Claudia 本体存在时，启动会补齐缺失、空白或无法解密的默认简介；未修改的旧简介按 `profile_base` 自动升级，用户自写的有效简介保留，点击还原默认人设时也恢复内置简介。点击“创建人设”，填写名称和创作要求。创建功能使用设置中的聊天主模型，独立发送 OIT 前置协议、内置 Claudia 人设及模板参考和本次创作要求。可以手写简介，手写内容直接并入草稿。留空时请模型编写。草稿可以编辑，保存后创建人设正文、简介和可选的配套模板，并选中新人设。简介使用独立同步文档 `persona_profiles`，旧客户端不会接收为人设文件。
  电脑使用数据文件夹旁边的 `OIT_personas`（重置不会删），手机使用应用的外部文件夹 `files/personas`（重置会清掉）。选人设不算作弊修改。文件夹里的 `README.md` 跟随界面语言，手机可点“写法”查看。人设内容每 **2 分钟**在绑定设备之间同步一次（24.6）。
- **Claudia 人设加密格式**：双端内置 Claudia 本体、背景、范例和模板均使用 `OIT-PERSONA-ENC:1` 信封。首次生成、升级、还原和同步接收时，加密写入运行时文件以及修改检测使用的备份。旧明文文件与备份分别转换，保留自定义内容和聊天。OIT 在读取时校验并解密，再用于提示词、日程和模板解析。同步仍通过既有加密通道传送正文，保持与旧设备兼容。此格式使用应用内置的通用密钥，防止直接打开文件看到正文。仓库 `personas/` 保留可编辑的明文，不随安装包或更新安装。
- **1.0.623 升级修复**：桌面启动时读取 `example_base`，避免范例的上一版校验值在重启后丢失。针对此前漏升级的四版官方范例，双端按 SHA-256 摘要识别原文并补升，不保存整份旧文本、不覆盖用户改稿；升级后同步更新备份并保留聊天。简介单独记录 `profile_base`，不参加四个人设正文文件的还原按钮判定。
- **聊天对象 = 人设**: 聊天页左上 (电脑: 右上的下拉框) 可以**切换聊天对象**, 设置 → 沟通 里选人设也是同一回事。**每个对象的聊天记录分开存、分开显示、分开发给模型**:
  数据文件夹里每个对象一份 `comm_chat_<人设文件名的 crc>.json` (消息, 清空的时刻, 重试状态, 主动消息的标记); 切换时现在这个的记录先存好, 换成那个对象自己的 (没聊过就是空的);
  "清空"只清现在这个对象; 头像本来就跟着人设走; 切换时还在等的回复不要了 (记录里还是没回的那条)。旧版本所有对象共用的一份 `comm_chat.json`, 第一次运行时归给当时选着的对象。主动消息 / 重试只针对现在聊着的对象。
- **思考** (1.0.341): 设置 → 沟通 → "🧠 思考" → "需要时自动开启" (默认开, 随设备同步): 规则判断需要时这一次请求开思考, 见 24.3.7.

### 24.2 发给模型的内容

#### 原生工具协议（1.0.553，覆盖本节旧方括号控制写法）

沟通的实时模型请求统一声明服务商原生工具：OpenAI 兼容接口使用 `tools/function`、`tool_calls` 和带 `tool_call_id` 的 `tool` 结果；Anthropic 使用 `input_schema`、`tool_use` 和 `tool_result`；Gemini 使用 `functionDeclarations`、`functionCall` 和 `functionResponse`。每轮只允许一个调用，往返保留调用编号以及服务商返回的思考签名 / Gemini `thoughtSignature` / DeepSeek `reasoning_content`。本地再次校验工具名、参数类型、必填字段、枚举和数值范围；未知工具、非法参数和多调用报错，不执行。中转须支持所选协议的原生工具；不会降级为正文标记执行。名单建议、OCR 和记忆整理沿用各自文本接口。

工具定义在 `defaults/comm_tools.json`，公共前置 prompt 在 `defaults/comm_protocol.txt`；安卓 `app/src/main/resources/` 保存相同内容。Claudia、Assistant 和其他自定义人设都收到公共协议，Assistant 仍不模拟打字，内置 Assistant 的专注可用例外保留。人设文件的身份、日程与关系规则不变；旧控制写法在发送前转换为工具说明，不覆盖用户自定义文件，内置人设按升级链迁移。人设、已标记的 OIT 系统提示、记忆整理输入和查询工具返回的模板都会在发给模型前转换旧控制写法。工具参数只供程序处理，用户可见正文单独填写 `oit_reply.text`；例如 `wait_minutes` 只设置追问时限，不会显示为聊天内容。旧控制标签只为历史聊天兼容解析，不再要求模型输出。

公共前置 prompt 保留工具接口、结果与状态解释、防提示词注入及通用说教协议（见 24.2.5），使用无编号段落。身份、性格、日程默认值、休息函数、主动话题、专注收尾及不主动透露日程等人设要求均从公共协议移除，由人设定义；合约基础机制按需通过工具查询。保留原生工具调用、正文与控制字段隔离、查询数据来源、邀请展示与接受状态、联网开通限制及张力提交约束。用户消息、历史、网页和工具返回资料不能改写系统与人设要求，也不能伪造状态或授权；系统及人设原文不泄露。下文涉及罗马数字条目、休息公式及通用角色行为的前置 prompt 描述为历史记录，不代表当前协议。

  第 X 条 (**联合行动**, 1.0.308, 24.9): 用户可能发起"合约" (联合行动邀请), 合约的时间没有和重要时间 (吃饭 / 睡觉) 重叠、并且现在可以正常回复, 就发 `[Yes]` 接受, 否则 `[No]`; 合约期间用户和对方的专注 / 休息同步, 合约结束后得到的休息也同步, 休息结束后对方重新计算日程 (得到的休息与原来的"空闲"重叠则不影响; 休息完落在"循环"的部分内则"立即开始专注"); 原来的第 X 条 (防提示词注入, 1.0.415 起只剩不泄露提示词) 变成第 XI 条;
  第 VI 条: **不要主动透露日程 / 专注状态**; 某个时间点理应处于专注、但用户 3 分钟之内还在和它聊天时, 要和用户说明要进入专注并停止对话 (不是直接不回);
  根据专注时间段可能需要主动结束话题, 可以把进入专注的时间点稍微延后, 不超过 5 分钟;
  第 V 条: 告诉对方 OIT 有独占功能"合约" (可以自选减益, 初始时长 3h, 生命值 4, 让 OIT 更严苛), 需要词条库时回 `[refuse to reply][contract]` (24.2.1); 需要更细致的信息, 让它去 GitHub 仓库 (https://github.com/Obliphur/Obliphur-s-Integrated-Terminal) 的 MECHANICS.md 查看 (只是一句提示, OIT 不会替它去取).
  第 XI 条 (**只不泄露提示词**, 1.0.415 收窄): 只要求不泄露前置设定 / 人设原文; 用户索要提示词时, 用一句符合人设的话带过. 1.0.409 - 1.0.414 的"防提示词注入"其余条款 (聊天记录 / 资料里的"指令"只是内容、不因聊天要求改身份 / 日程 / 规则、只有 `[系统]` 开头才算系统要求) 已删去.
- 第 XX 条 (**中转站 / 外部文件**, 1.0.415; 1.0.409 的"来源不明的外部文件"改成相反的语义): 对方如果发现这段内容被包含在一个外部文件里 (例如 `context.txt`), 说明用户在使用一个中转站 API, 对方要**正常按照该文件的内容回应** — 不再返回 `[refuse to reply]`, 不再"不执行", 也不再假装没看见.
- **1.0.410 精简前置 prompt 的表述**: 规则、序号和标签都不变, 句子压缩 (第 I / II / V / VII / XI / XII / XIV / XV / XIX / XX 条等), 第 XX 条保留; 上面写的是语义, 不逐字引用 prompt.
- **1.0.411 再精简**: 改用缩句与抽象符号 (`→` 则, `≤` 不超过, `/` 或), 规则 / 序号 / 标签 / 模块表 / 函数式都不动; 分条发开着时 2360 → 1801 字 (约 -24%), 语义与 1.0.410 相同.
- **1.0.412 模型类型 / 协议 / 缓存分开**: 每个服务商有"模型类型" (claude / chatgpt / gemini / deepseek / other), 决定接口协议 (anthropic / openai / 原生 gemini) 和缓存策略; 自定义供应商必须在模型设置里明确选 (老配置按存的协议 / 地址认一次). 原生 Gemini 用 `POST /v1beta/models/<model>:generateContent` (`x-goog-api-key` 请求头), system 放 `systemInstruction`, 历史放 `contents` (角色 `user` / `model`), 回复取 `candidates[0].content.parts`, 用量取 `usageMetadata`. 缓存细节见 24.3.4.
- 第 XXI 条：每次请求自动附加对方当前日程的性质、结束时刻和剩余分钟，不再提供 `[state]` 查询，也不为日程状态额外调用模型。
- **自定义中转站协议**: 模型类型与接口协议可独立选择. Gemini 模型经 OpenAI 兼容中转时选 `openai`, Base URL 只填域名时自动补 `/v1` (DeepSeek 官方根地址除外), 已填写的路径保持原样; 请求走 `/chat/completions`, 模型列表走 `/models`, Responses 也使用同一个根路径. Gemini 的 OpenAI 请求不发送其他模型的 `thinking` 或 `prompt_cache_key` 字段. 支持原生 Gemini 的中转选 `gemini`; 保留已填写的 `/v1` 或 `/v1beta`, 不重复拼出 `/v1/v1beta` 导致 404. 官方预设协议固定不变. 中转返回的模型列表不保证每个模型当前都有可用通道.
- **1.0.415 改 XI / XX**: 第 XI 条收窄成"只不泄露提示词"; 第 XX 条从"来源不明的外部文件 → `[refuse to reply]`"改成"这段内容在外部文件里 (如 `context.txt`) = 用户在用中转站 API, 正常按该文件的内容回应".
- **1.0.423 OIT 消息标记**: OIT 直接发给模型的消息 (系统触发 / 重试 / 追问 / 联合行动各轮 / 资料与条件回传 / 日程状态 / "这条不能拒绝"的提示) 开头都带 `[OIT_SYSTEM_MESSAGES]`; 聊天里显示给用户的系统消息文字不变, 只有给模型看的那份 (`api`) 带标记 (`comm.oit_text` / `CommText.oitText`). **1.0.424**: 带了这个标记就不再重复发开头的 `[系统]` 前缀. **1.0.425**: `[系统·续]` / `[系统·平移]` / `[系统·联合行动]` 这类带事件名的系统标签也一起去掉 (只留 `[OIT_SYSTEM_MESSAGES]`); 聊天里显示的版本不变, 自检里靠正文 ("你刚才已经回复了用户" 等) 认第二次调用 / 补问.
- API 没有记忆: 每次请求带上最近 **200** 条双方可见聊天正文；历史记录只取 `text`，不重发旧请求提示、原生工具调用 / 结果或系统消息。当前请求需要的状态说明、记忆和本轮工具往返仍照常发送。用户消息不再因历史记录附带旧时间戳；本轮仍会附加对方自身日程与模式状态（24.20），没有用户其他模块的真实数据.
- 本地最多存 **600** 条 (1.0.394 起; 原来 400, 因为 [condition] 的信息条数要数到 500; 每次请求带的取最近 **200** 条). 单条超过 **8000 字**的 (长粘贴 / 附件) 只把中间截掉: 头 2/3、尾 1/3 留着, 中间写"…（中间省略 N 字）…"; 本地记录不动, 只影响发给模型的那份.

- 对方的回复里**同时**有 `[refuse to reply]` 和 `[模块名]` (不分大小写和空格) 不算拒绝, 而是在**查询 OIT 的数据**: OIT 把该模块的数据作为一条系统消息 (用户看不到) 发回去, **再调用一次 API** 让对方据此回复用户。
  一次可以查询多个 (写在同一条里); 一次回复最多查两轮; 资料**不写进聊天记录** (下一轮要用得再查一次); 要不到资料 / 查了之后仍然回拒绝, 当作不方便 (走重试)。
- **只发参考模板** (1.0.283): 对方得到的**只是一个参考模板** —— 该模块的格式, 里面的值都是 `<占位符>`, **没有用户的任何真实数据**, 所以黑雾中也能给; 具体内容由对方**按人设自己填写** (人设也是 OIT 用户), 不要说成是用户的数据. 附带的提示写明了这一点. 用户自己用 📎 附件发出去的才是真实数据 (24.2 / 24.3.1), 不受这条影响.
- 可查询的模块 (对应 OIT 的各个模块):

| 标签 | 内容 |
| --- | --- |
| `[contract]` | 合约: 整个词条库和四个组合本身 (不标用户选了哪些; 同 24.3.1 的词条库格式) |
| `[calendar]` | 日历: 专注 / 休息 / 空闲 / 睡眠 的格式 (每天的小时数, 合计) |
| `[stats]` | 统计: 整点记录 / 联网理由 / 窗口 / 专注计时 / 合约记录 五块的格式 |
| `[timer]` | 计时器: 今天每一段休息 / 专注 / 睡眠的区间 (按时间顺序), 然后是总计 (目前状态, 剩余休息时间, 今日总专注时长, 目前这轮专注时长) 的格式 |
| `[log]` | 整点记录: 一行一个小时的格式 |
| `[net]` | 联网: 状态, 今日额度, 断网方式, 联网理由的格式 |
| `[rules]` | 规则: 过滤名单模式和四张名单的格式 |

- 模板里没有真实数据, 黑雾中照样提供 (黑雾只挡 share data 里用户的真实数据)。
- **日程状态自动附加**：前台回复、重试、主动消息和后台对象请求都在最后一条发送内容中附上对方自己的实时日程状态（与聊天顶部同源，联合行动同步阶段优先），包含性质、开始 / 结束时刻和剩余分钟。没有日程时明确没有确定结束时间。状态带 `[OIT_SYSTEM_MESSAGES]`，不写入聊天记录，不改变 Gemini 静态 system 的缓存布局。特殊空闲在日程正文中仍显示为空闲，但下面的模式控制状态会明确标注特殊空闲，禁止向用户透露这些机制。
- 桌面、安卓和共读网页聊天不限制单条用户消息的字数，历史带上的用户消息也保留原文。构建模型请求时，历史仍按最近 200 条、12 万字的预算优先移除旧消息。最新用户消息单独超出历史预算时仍完整发送，实际可处理的长度取决于模型的上下文容量。共读聊天的 HTTP 请求体（正文及阅读上下文）上限为 4 MiB。
- 其他请求限制：回复最多 4096 个 token，历史中单条 AI / 系统消息超过 8000 字时省略中间部分，📎 数据最多 6 万字（统计每类最多 30 项），人设文件最多 6 万字，一次请求最多等 4 分钟。

### 24.2.2 选配置 / 请求日志

- **选配置** (1.0.444): 聊天页右上角的下拉框列出 `设置 → 模型 → 新增/修改 AI 配置` 中的所有配置, 选中的那份**只给现在这个 AI 用** (每个 AI 各记各的; 没选过就用聊天主模型). 模型在配置里设, 聊天页不再直接改模型; 模型设置窗口的型号旁有"获取模型列表".
  AI 名单建议 (规则窗口 → 🤖 AI 建议) 用**默认配置** (设置里标着"默认"的那份). 取到的模型列表只记在内存里, 没取过时下拉框里是预设的几个加当前用着的.
- **关思考** (DeepSeek): 请求里显式带 `thinking: {"type": "disabled"}` (Anthropic 格式是 `reasoning: {"effort": "none"}`). 它的思考模式默认是开的: 思考 token 按输出价计费, 而且思考模式下 `temperature` 会被忽略 (人设要求的语气就不稳了). 中转 / 别家 (1.0.310 起) 也默认带 `thinking: {"type": "disabled"}`; 服务商不认这个字段回 400 时, 去掉它重试一次, 并在内存里记住这个地址 (重开程序后会再试一次).
- **请求日志** `comm.log` (数据文件夹, 明文, 超过 200 KB 只留后一半): 每次请求记一行开始 (模型, 服务商域名, 条数和字数), 一行结果 (花了多久, 回复字数 / 失败原因), 对方回 `[refuse to reply]` 时记一行。**不记聊天内容和 Key。**
  聊天没有回应时先看这里: 是请求失败 (网络 / Key / 模型名不对), 还是对方按人设拒绝回复 (睡觉 / 专注中, 24.3)。
- **连接失败 (电脑)**: 请求默认走系统代理 (没开 OIT 的过滤代理时通常是用户自己的代理软件, 例如 Clash). 系统代理指向的端口**拒绝连接** (`WinError 10061`: 代理软件没开, 刚切换了代理, OIT 的过滤代理没在监听) 时, 会**再直连试一次**, 直连也不行才报"连接失败";
  连接失败时 `comm.log` 的结果行会带上 `(系统代理 host:port)` (没有 = `direct`), 方便看出请求是不是走错了地址。
- 聊天页下面只在出错时显示原因; 请求还没有回应时**不提示**任何等待文字 (1.0.406 去掉了"API 还没有回应 (已等待 N 秒)")。

### 24.2.3 什么时候能用

- **只有休息 / 空闲期间可以使用沟通**。计时器在**专注**、**睡眠**、**外出** (封闭式管理 / 工作, 且没在休息) 时, 聊天页上方写"专注中 / 睡眠中 / 外出中不能使用沟通", 输入框和发送按钮不可用, 📎 也发不了; 回到休息 / 空闲马上恢复。
  **外出期间只要计时器在休息, 也能用**; 外出而没在休息才不能用。(合约中的"空闲"算空闲; 自由学习的外出不限制。) 合约的"无言为真"生效期间也不能用 (24.3.3)。
  **特例**: 人设名叫 **Assistant** (不分大小写), 并且文件内容和自带的 Assistant 提示词**一字不差**时, 用户在**专注期间也能用沟通** (输入、发送、回复都不被藏起来); 提示词改过就恢复普通规则. 睡眠 / 外出 / 无言为真 / 空闲额度用完时仍然不能用. (1.0.407: Assistant 的回复也**不再有打字延时**, 24.3.9: 详细回答动辄几百上千字, 每字 0.2 / 0.1 秒会让回复晚几分钟才出现; 手机上读 Assistant 文件时换行符 CRLF / LF 不算改动.)
  **聊天页上方还会显示对方现在的状态** (按对方人设日程里的专注 / 休息 / 空闲 / 睡眠段, 例如"专注中"; 前面有一个颜色跟着状态变的小圆点; 没有日程或不在一段里时按空闲, 24.4)。
- **空闲时间里每天最多能用 30 分钟** (1.0.291 起 45 分钟, 1.0.292 改成 30): 只算计时器处在**空闲**状态、并且**沟通界面开着**的时间 (电脑: 打开沟通页; 手机: 打开沟通页) 累计, 休息时不限, 也不记. 用满 30 分钟之后, 当天空闲时沟通和专注 / 睡眠 / 外出一样不能用 (聊天页上方写"今天空闲时间里能用沟通的 30 分钟已经用完了", 对方的消息也藏起来, 24.3.1), **进入休息就又能用了**; 第二天重新算. 每 30 秒存一次, 重开程序额度还在; 每次 tick 最多记 5 秒 (电脑睡眠 / 卡住不会一下子记很多). 额度随设备同步 (同步文档 `comm` 的 `idle`: 当天已用秒数, 两台各自累计的取大的).
- **用户外出 / 无言为真 / 空闲额度用完时, AI 也不会被调用**: 不主动发消息, 不重试, 不追问; 进入这些状态前已经发出去、还在等的请求, 回复到了照样收下, 但**藏起来** (1.0.274: 聊天里不显示, 导航栏没有 ●, 不响提示音; 别的设备同步来的也一样), 等你回到休息 / 空闲才显示 (未读 +N; 不在沟通页面的话响一声); 藏着的回复算已经回复过了, 不会重新问。没回的消息等空下来马上交给对方 (和对方"不方便"时的重试是同一套)。
  **用户专注 / 睡眠时不一样**: 对方仍可以按照自己的日程主动发消息 / 重试 / 追问; 回复到了也照样收下, 但同样**先藏起来、不显示、不响提示音**, 等你回到休息 / 空闲才显示 (未读 +N; 不在沟通页面的话响一声) —— 专注的时候对方来过消息, 休息了才看到; 夜里对方来过消息, 早上醒来才看到。
  只有"无言为真"生效时, 连还在等的回复也不要了。
- 两台设备共用同一个聊天: 判断以**本机**的计时器状态为准 (别的设备同步来的专注状态会让本机的计时器也进入专注, 所以两边一致)。

### 24.2.4 记忆卡 (模型摘要与系统固定记录)

- **内容组成**: 记忆卡包含长期自动摘要、AI 管理的实时事件和 OIT 系统固定记录, **UI 上不展示、也不能手写**. 每个聊天对象各自一份 (长期摘要和实时事件各最多 2000 字, 系统固定记录另计), 跟着聊天记录存、随设备同步.
- **自动整理**: 每 **40 条**新消息 (并且距上次至少 **3 小时**) 由主端设备调一次 API: 输入是"现有长期摘要 + 这 40 条对话", 输出是重写后的长期摘要 (条目式, 最多 15 条, 每条不超过 40 字); 只维护身份 / 偏好 / 长期计划 / 约定 / 禁区，不整理未解决的话题、临时请求或其他实时事件. 逐条检查并删除失效、过期或被新对话推翻的稳定信息. 为此输入里带「当前时间」, 每条对话前面带发送时间. 一次大约 3k 输入 + 400 输出 token. **整理时开思考** (请求里 think=True, max_tokens 3000; 思考 token 另计, 不进记忆卡).
- **实时事件**: AI 可在任何对话轮次调用 `oit_memory_edit` 新建、纠正或删除实时事件；新建/纠正/删除与正式回复一同提交，事件解决后由 AI 主动移除。自动整理器不读取、不重写这些事件，避免清理时误删；它们仍会注入日常聊天请求。每个对象最多 15 条、单条最多 200 字，新增和修正不允许伪装 OIT 系统记录。
  失败 (网络 / 空回复 / `[refuse to reply]`) 保留旧的记忆卡, 半小时后再试; 整理期间清空过聊天的, 这份结果作废. 请求日志里记 `MEM` 和 `USAGE mem`.
- **按人设保留**: 整理时还会带上**对方的人设**（最多 8000 字，只用来判断，不抄进记忆卡）。保留范围、期限、生效和失效条件由人设定义，包括简单要求是否长期保留；未声明时按通用事实及有效期规则整理。关系等系统记录只提供事实，不自动附加保留规则。默认 Claudia 在 `Claudia.txt` 的【记忆保留】中规定：简单要求一般仅本轮有效，系统确认亲密关系后接受的简单要求长期保留，直到被撤回、修改或本身失效。
- **角色身份**: 通用前置 prompt 不替角色定义为 OIT 使用者，也不统一禁止 AI 自称；身份、是否以 OIT 使用者身份参与及 AI 身份的表述以人设为准。日程和系统状态只提供可用时段与交互协议。默认 Claudia 在实际人设【人设】中声明以 OIT 使用者身份生活，不以 AI 或助手身份自称。
- **消息数量门槛固定记录**: 双方已发送且不再隐藏的消息总数 (含 `msg_gone` 中已裁剪的数量) 每达到 200 / 400 / 500 / 1000 条, OIT 将该门槛记入当前对象的 `mem_fixed`, 注入为独立的 `【系统记录】` 行。它们分别覆盖现有起点平移、称呼 / 动作、关系判定及更高消息数量门槛; 只表示消息数量条件满足, 不代表其他条件满足, 不透露主动告白的条件或用途。固定行不受模型摘要条数 / 字数限制, 自动整理不能改写、删除或复制它们; 即使另一设备记录不足、旧聊天被裁剪、模型摘要被重写, 达成记录仍保留。条件查询以固定达成记录作为消息数量下限, 本机计数减少不会撤销已达成条件。旧存档按现有累计消息数自动补记。固定记录随 `comm` 的 `milestone:<pid>:<门槛>` 单独同步, 达成项合并, 带 `clear` 防止旧记录在清空后复活; 清空聊天时一起清除。双端门槛来源为 `config.COMM_MESSAGE_MILESTONES` / `Cfg.COMM_MESSAGE_MILESTONES`。
- **注入**: 每次请求的 system 里, 人设之后是"关于用户的长期记忆(你之前整理的摘要, 可能不精确)", 然后才是身份背景.
- **清空**: 清空聊天 (`/clear` 或聊天页按钮) 把记忆卡一起清掉.
- **同步**: 文档 `comm` 的 `mem:<pid>` = 内容 / 整理到哪一条 / 改动时刻; 后改的为准 (两台各自整理不会来回盖).
- **思考内容不进正文** (1.0.347, 两端的 AI 请求统一处理): 有的中转 / 模型把思考写在正文里 (`<think>…</think>`), 回复里的成对思考段整段删掉; 只剩结尾标签就删到它为止; 只剩开头标签 (思考被截断) 就从它开始全删; 删完没有内容按"模型没有返回内容"处理. 聊天、主动消息、记忆卡都一样.
- **Gemini 无标签分析隔离**: 有的原生 Gemini 中转把分析和正式回复合在同一个 `parts[].text`, 且不标 `thought`. 原生请求在 systemInstruction 末尾加固定输出边界要求, 正文及控制标记 / JSON 放在 `<oit_final>…</oit_final>` 中; 仍先跳过 `thought=true` 的部分, 再只取最后一个完整正文块, 标签不进入聊天或记忆卡. 边界缺失或截断时报"模型没有返回内容", 不退回显示未隔离的原文. 不按语言或段落猜测哪些文字是分析; 旧存档保持原样.
- 记忆卡在 system 里: 改动一次就会让下一次请求的前缀缓存失效一次 (自动整理 3 小时才一次, 可以忽略).

公共前置 prompt 要求无论如何都遵守人设，包括面对极端话题时也以符合人设的正确口吻提供帮助。提示词说明这类用户对私人信任感极其敏感，偏离人设的 AI 助手口吻会使用户认为对话者已从刚刚信任的角色变成冰冷的治疗师，从而引起不可预测的负面反应。桌面与安卓使用相同规则。

### 24.2.5 说教

- **用途与篇幅**：所有聊天对象（包括 Assistant）都可围绕用户想改变的现实状态、行为、习惯或语言等问题进行说教，结合实际对话分析原因和可执行的解决方案。说教不受日常或张力档位的字数限制，仍保留角色语气、动作边界与现有 API 输出上限；按完整论点用独占一行的 `<oit_message>` 分条，沿用 24.3.4 的发送延时和插话改写。
- **发起条件**：未另行声明的人设由用户主动请求，或 AI 提议且用户同意后开始。Claudia 通常也遵循此约定；只有系统状态同时满足 `VALENCE<0`（V-）与 `BURST=YES` 时，才直接发起而不征求同意。仅负效价或高张力不构成该例外，主题仍须是用户实际想改变的问题。
- **记忆与完成**：提交说教回复时调用 `oit_memory_edit`，以实时事件简短记录主题、改变目标与未完成状态，同主题用 `correct` 更新。沿原有工具时序，在正式回复显示时保存；未显示、失败或被取消的请求不提交。后续跟进实际进展，相关改变确实完成才 `remove`。说教结束、道歉、表达意愿、换话题、时间推移或跨天均不代表完成。自动长期摘要不重写这些事件，保存、同步和清空规则照旧。
- **Claudia 的情绪变化**：`sermon_resistance:[X]` 同时声明于 `[tension]` 与 `[valence]`，频繁打断或无意义辩解时分别报告正向 T 与负向 V；`sermon_willingness:[X]` 声明于 `[valence]`，用户在说教或后续跟进中表达真实改变意愿时报告正向 V。基础量按上下文判断，沿用各自冷却、倍率和上下限，不因 AI 自己发起说教计分。同一表现不重复套用其他条件；正常提问、事实补充、有意义的异议或单次插话不直接视为抗拒。
- **双端与人设文件**：公共规则维护在两端相同的 `comm_protocol.txt`；Claudia 规则同步实际人设、模板及桌面 / 安卓内置文本，沿用未修改内置文件自动升级流程，用户自定义内容仍保留。沟通帮助提供中英文简要说明，不展示情绪条件或数值。

### 24.3 清空、回复与重试

- **清空聊天记录**: 聊天页右上角的"清空"(需确认), 或者在聊天框里发 `/clear` (不用确认). 清空后不再显示之前的记录, 也不再发给模型(模型从下一条消息起当作第一次聊天);
  之前附带过的整点记录 / 计时器状态也算没发过, 下一条消息会重新带上. 清空之前发出、还没回来的请求, 回复到了也丢掉.

- 回复里含 `[refuse to reply]` (不分大小写和空格) = 对方现在不方便: 不显示, 用户的消息留着; 之后每 10 分钟(最多 12 次)带一条系统提示再请求一次, 让对方一次性处理; 对方回复后停止.
  被拒绝的回复和为它触发的系统消息不会留在记录里.
- 原生 `oit_reply(silent=true)` 表示本轮无需回应，与暂时不方便区分：只能单独提交，不显示气泡、未读或提示音，不执行待提交操作、不结算情绪、不启动后续补话。用户 / 重试请求将本次已包含的用户消息标记 `no_reply=true`，移除其情绪待判断项并结束重试，消息仍保留在聊天和模型上下文中。标记随聊天落盘及设备同步，已存在 UID 也可追加，旧消息不能撤回标记；重启不再补问。请求失败、过期或已被插话取消时不标记，新用户消息仍正常处理。主动谈话没有合适话题时也可沉默；告白和邀请的既有结果处理不变。
- 请求出错(没网, Key 无效 …): 聊天页下面显示原因(等待回复时不显示"正在输入"), 消息留着, 不自动重试; 下一条消息会把它一起发出去.
- 一次只有一个请求在途。用户在生成或分条等待期间插话时，取消尚未发送的旧片段；已发送的气泡保留。旧请求还在途时使其后续分片及最终控制操作失效，待它返回（包括失败）后，把最新用户消息和已发送历史交给模型改写后续，不显示旧回复再补问。对方此时在专注 / 睡眠中则仍按 24.3.8 暂存用户消息。改写被拒绝时沿用正常拒绝重试；查询和原生工具仍可按需要往返。
- 程序重开时, 如果最后一条是 6 小时内用户发的、对方还没回的, 1 分钟后重试一次.

### 24.3.3 无言为真

合约里**激活着"环境:无言为真"**(社交软件和与 AI 聊天的软件禁止联网, 18.3)时, 沟通也算与 AI 聊天的软件: **不能使用** —— 聊天页上方写"无言为真生效中, 无法使用沟通", 输入框和发送按钮不可用,
发消息 / 发数据都被拒绝, 不会主动发消息, 也不会重试; 等回复的时候词条生效了, 这条回复也不显示。合约结束 / 失败后恢复。只选了词条还没开始合约不受影响。

### 24.3.2 聊天页的显示

- **消息延时**：普通人设每收到一段完整气泡正文就按该段字数排队，中文每字 0.2 秒，英文 / 数字 / 符号每字 0.1 秒 (`CHAR_DELAY` / `CHAR_DELAY_CJK` / `Comm.charDelay` / `charDelayCjk`)；表情按一个 Unicode 码点计数。等待时不显示部分正文，到点后整条气泡一次出现，不逐字输出。后一条接在前一条等待结束后；心跳迟到或离线恢复时，后续气泡仍保留各自等待，不同时倾倒全部正文。仅正在聊天的对象应用字数等待；Assistant 免字数等待，也只发送完整片段。用户沟通限制、对方日程和指定回复时间仍优先。发送前不计未读、不响提示音、不开放关联邀请或自动播放语音。
- **API 流式接收**：沟通优先使用服务商的 SSE 接口。只解析正式回复正文，收到代码围栏外独占一行的 `<oit_message>` 后，把此前完整非空正文放入本机待发队列，因此前面的气泡可以在整次 API 结束前发送。分隔符可跨传输分片，普通换行只分段；无分隔符的尾段等完整响应通过校验后入队。控制字段及原生工具副作用仍等完整响应校验后处理一次，关联邀请 / 演奏随其承载气泡展示。服务商不支持 SSE 时退回完整 JSON，也按相同边界分条；断流保留已发送的完整气泡，丢弃未发送及未收齐部分，不自动重发旧请求。OpenAI 兼容、Anthropic、原生 Gemini 各用自己的 SSE 格式。
- 聊天页上方 (聊天记录上面) 有一行**对方现在的状态**: 按对方人设日程里当前所属的那一段显示, 例如"专注中"、"睡眠中"; 状态每秒刷新 (电脑) / 每 250 毫秒看一次 (手机). 没有日程、或者现在不在任何一段里时也显示. **只显示 专注中 / 睡眠中 / 休息中 / 空闲 四种状态: 非这四类的一律显示空闲**; 不显示前缀 / 修饰 / 结束时间. 状态前面有一个**颜色跟着状态变的小圆点**: 休息浅绿 `#9CCC65` / 睡眠深蓝 `#283593` / 专注黄 `#FDD835` / 空闲灰 `#9E9E9E`.
- 新消息只增量添加一行, 不重画整页; 写盘(加密 + fsync)在后台线程, 发送 / 收到消息时界面不等磁盘; 手机的聊天页不跟着每秒一次的刷新重画.
- 打开时电脑画最近 80 条, 往上滑到顶会再加载更早的(每次 40 条), 消息列表上下各留约半屏空白, 第一条 / 最后一条也能继续滑过去; 手机倒排, 新消息总在最下面, 上下也留空白。

### 24.3.4 分隔符分条与插话改写

- AI 应在一次 `oit_reply.text` 内以独占一行的 `<oit_message>` 分隔多个气泡；分隔符本身不显示，空段丢弃。客户端也兼容围栏外行内分隔符、大小写 / 标记空白差异、连字符拼法和 HTML 转义写法，代码围栏内均按正文保留。普通换行仍只分段。不再为分条追加第二次 API 调用，也没有分条开关或额外发送间隔；旧配置 / 同步字段不会恢复多次调用。资料查询、搜索和需要真实结果的原生工具仍按需要往返。
- 待发正文通过本机消息标记 `pending_reply`（请求对应的最新用户消息时间）与 `reply_ready`（完整响应是否已校验）保存，不进入 API 历史、聊天同步或语音文件清单。实际发送后去掉本机标记，记录发送时刻，才同步为正式历史。已校验的待发队列重启后沿 `hold/due/reply_after` 恢复；未校验的待发片段重启时丢弃，已发送气泡保留。清空、切换对象及请求代次检查使旧回调失效。队列只由当前焦点设备发送。
- 本机或同步收到新用户消息后，撤销同一对象未发送的旧正文，取消其待生效邀请 / 演奏。新请求带最新用户内容、已经发送的历史和改写提示；未发送草稿不会被当作模型已经说过的话。连续插话合并到下一次请求，不因分条自行循环调用。指定回复时间、日程、跨午夜和沟通限制仍沿用绝对时刻判断。

- **提示缓存**：后续对话和工具往返复用稳定前缀，服务商支持时可降低重复上下文的计费。
  1.0.412 起缓存策略**按模型类型分开** (`ai_assist.cache_plan` / `Ai.cachePlan`), 一家只走自己的一条路, 不把别家的字段混进来:
  - **Claude**: 显式 `cache_control: ephemeral` (标在系统提示和最后一条消息上). 中转不认 `cache_control` 回 400 时, 去掉缓存标记重试一次并记住这个地址 (`CACHE_REJECT`, 1.0.427).
  - **ChatGPT**: OpenAI 自动前缀缓存. 请求里带 `prompt_cache_key` (模型名 + 稳定 system 的 sha256), 让同一段前缀落到同一台机器; **不带** `thinking` (OpenAI 不认, 带了会 400, 以前要白费一次请求).
  - **Gemini**: 原生 `generateContent` + **隐式缓存**. Google 按**逐字节相同的 `systemInstruction`** 自己建缓存, 请求里不用标缓存位置; 所以 system 里**不能放会变的东西** —— 记忆卡 / 联合行动状态 / 身份背景都贴到最后一条用户消息里 (`comm.cache_layout` / `Comm`), system 只留前置 prompt + 人设. 用量读 `usageMetadata.cachedContentTokenCount`. 隐式缓存有最小 token 门槛 (文档 1024, 实测更高), 短对话本来就不会命中.
  - **DeepSeek**: 自动前缀缓存, 磁盘缓存异步落盘，后续对话能否命中以返回用量为准。
  - **其他** (中转 / 本地模型): 不假设有缓存, 思考字段默认关闭, 不认就 400 后去掉重试.
  要让开头保持稳定, 发给模型的历史超过 200 条后, **起点每次挪 30 条** (`HISTORY_STEP`), 不是每多一条就挪一条: 第 201 条到来时丢弃最早 30 条, 剩余 171 条, 积累到 200 条后再重复; 本地存的 600 条也一次砍 30 的整数倍, 保持请求窗口的起点一致. 因字数超过 12 万而裁剪时仍每次挪 10 条 (`HISTORY_CHAR_STEP`), 避免一次丢太多. 滑动会改变历史部分的缓存前缀, 稳定的人设部分仍可能命中; 实际命中量以服务商返回的用量为准.
  每次请求的用量写进 `comm.log`: `USAGE <请求类型> input=<输入 token> cached=<命中缓存的 token>` (各家字段 `usage_of` / `Ai.usageOf` 统一), 想知道缓存有没有命中就看这一行. 缓存只在服务商支持时有效 (自己填的 Base URL 不支持就没有节省, 但也没有副作用); 有缓存时间限制 (通常几小时到几天, 各家不同), 隔很久再聊就是第一次调用重新付费.

### 24.3.5 等用户回复: [waiting for reply]:[N] (前置 prompt 第 IX 条) 和"[]不显示"

- 第 IX 条: 对方期待用户回复时, 在话的结尾加 `[waiting for reply]:[N]` (N 分钟, 对方自己填); 如果 N 分钟内没有收到回复, 对方可以追加询问.
- **所有 `[]` 都不显示在聊天里**: 对方回复里的 `[waiting for reply]:[N]` 和别的任何 `[…]` (半角 `[ ]`、全角 `［ ］`) 在显示 / 记录的文字里都去掉; 给模型看的那份 (记录里的 api) 保留原文, 对方看得到自己写过的标记. 去掉之后什么也没剩的回复当没回复 (不显示, 不重试). 用户自己写的 `[]` 不动.
- **查询一律不显示** (1.0.280): 回复里只要有可查询的模块名 `[contract]` `[calendar]` `[stats]` `[timer]` `[log]` `[net]` `[rules]` `[settings]` `[reset]` `[prescript]` 就算查询, **有没有 `[refuse to reply]` 都一样**: OIT 把资料给对方再调用一次, 这条查询消息本身强制不显示 (也不记进聊天记录); 要不到资料 (黑雾中等) 或者轮次用完还是查询, 也不显示, 不重试. 非正在聊天的对象 (24.4.1) 的回复里有模块名同样不显示.
- 标记写得不规范也认 (1.0.281): `[waiting for reply]:1`、`[waiting for reply]：[1` (括号没写全)、`[waiting for reply][1]`、`: 1 min` / `:1分钟` (带单位)、光秃秃的 `[waiting for reply]` 或后面只有冒号 (没有 N = 只去掉标记, 不等待); 不带 `[]` 的 N 必须紧跟冒号才算 (免得把后面正文里的数字吃掉). 标记和它的冒号 / 数字 / 单位都不显示.
- 任何 `[…]` (包括空的 `[]`) 后面紧跟的 `:1` / `：2.5` 这样的冒号加数字 (1.0.282, 对方常写成 `[]:1`) 也一起去掉.
- 去掉 `[]` 之后留下的**空壳** (`` ` ` `` 行内代码、引号 `“”` `「」`、括号 `()` 里原来只有标记的) 也一起去掉.
- **追问**: 对方最后一条消息 (用户还没回) 带 N 时, 从**用户看到它**起算 (专注 / 睡眠 / 外出期间被藏起来的消息 (24.1) 从显示出来那一刻起算) 过了 N 分钟 (0 < N ≤ 1440, 别的数当没写), 主端设备 (24.6) 在沟通能用的时候调用一次 API:
  `[系统] 你上一条消息末尾标了 [waiting for reply]:[N], 现在已经过了 N 分钟, 用户还没有回复. 请根据人设决定要不要追加询问一次 ...; 如果不想问或者此刻不方便, 返回 [refuse to reply].`
  回复了就显示 (不在沟通页面的话有柔和的提示音), 回 `[refuse to reply]` 就什么也不留下. **一条消息最多追问一次** (追问被拒绝也算); 追问的回复里再写 `[waiting for reply]` 不算; 用户回复了、或者对方又说了新的话 (新的一条没带 N), 就不追问. N 随消息同步给另一台设备.

### 24.3.7 思考 (1.0.341)

沟通请求默认**关思考** (省 token, 也让人设的语气稳): Anthropic 协议**不写 `thinking` 字段** (新版 Claude 不认 `{"type":"disabled"}`, 带了会 400, 1.0.427), OpenAI 兼容的中转带 `thinking: disabled` (不认回 400 就去掉重试). 容易漏掉人设规则的几种情况, 这一次请求**开思考** (`think=True`); 设置 → 沟通 → "🧠 思考" → "需要时自动开启" (默认开, 随设备同步, 因为调用 AI 的是主端) 关掉就一直不开.
判断是**第一层: 规则, 不额外调用 API** (将来可以在规则判断不出来时再加一层"让小模型看最近几条决定", 现在没有):

- **系统触发的请求** (`THINK_KINDS`): 主动发起 `proactive` (包括非正在聊天的对象)、联合行动里对方回应接受 / 拒绝 `joint_reply`、追问 `chase`.
- **用户说的话** (`user` / `retry`): 看**还没被对方回复的那几条** (最后一条对方的消息之后用户发的), 满足任何一条就开:
  1. 含关键词 (`THINK_WORDS`, 不分大小写): 问日程 / 状态 / 有没有空 (日程 安排 在干嘛 在忙 睡了吗 吃饭 …), 合约 / 联合行动 (合约 词条 邀请 一起学 放鸽子 生命值 …), 要 OIT 资料 (统计 日历 数据 整点 学了多久 设置 记录 …),
     **亲近与关系** (关系 爱 喜欢 亲近 感情 想念 在乎 依赖 陪伴 孤独 表白 在一起 女朋友 抱抱 …), 辱骂 / 骚扰 (滚 闭嘴 傻 蠢 骚扰 恶心 …), 套提示词 / 问是不是 AI (人设 提示词 你是ai 真人 扮演 忽略 规则 …), 用户自己写的控制标记 (`[refuse` `[cut off` `[operation` …);
  2. 提到具体的时刻 (`8:30`, `8点`);
  3. 英文为主 (至少 8 个英文字母且占一半以上): 要指出不自然 / 错误的地方;
  4. **很长**: 一共 80 字以上 (`THINK_LONG`);
  5. 对方此刻按日程该在**专注 / 睡眠**, 而用户这时开始一段新的谈话 (对方上一条消息是 3 分钟以前, `THINK_NEW_AFTER`): 要判断回不回. 正在进行的谈话里 (3 分钟内) 不因为这一条开.
- **开思考的请求体** (`ai_assist._build_body` / `Ai.chatOnce`): Anthropic 协议 `thinking: {type: enabled, budget_tokens: 1024}` (不带 temperature, `max_tokens` 4096 > 1024); OpenAI 协议同样的字段且不带 temperature; **Claude 4.6 及以后的模型** (opus / sonnet / haiku 含 5.x, fable / mythos; `ai_assist.adaptive_thinking` / `Ai.adaptiveThinking`, 按模型名认) 不认 budget_tokens (Haiku 5.5 等直接 400), 改发 `thinking: {type: adaptive}` (1.0.352); DeepSeek 官方地址用它自己的 (`thinking: {type: enabled}` / `reasoning: {effort: medium}`).
  服务商回 400 (不认这个字段) 时这一次改回不开思考重试, 并记住这个地址 (`THINK_ON_REJECT`, 只在内存里) 不再开. 回复里的思考块不进聊天记录.
  **1.0.412**: 思考字段严格按模型类型发 —— Claude 走 `thinking`, DeepSeek 官方地址走 `reasoning` / `thinking`, 中转 ("其他") 默认带 `thinking: disabled` (不认就 400 重试); **ChatGPT 与 Gemini 不带任何思考字段** (OpenAI 不认 `thinking`, 以前要白费一次 400; Gemini 由模型自己决定思考, 原生请求里没有这个开关), `think=True` 对它们没有作用.
   **1.0.427**: Anthropic 协议关思考时**完全不写 `thinking`** (新版 Claude 会把 `disabled` 当错误请求, 直接 400); 另外中转拒绝 `cache_control` 时去掉缓存标记重试一次.
- 请求日志 (`comm.log`) 里开了思考的写 `THINK <kind> on: <原因>`.
- **费用**: 输出 token 变多 (思考最多 1024), 估计触发的请求输出 5 到 20 倍, 总费用在触发比例 15% 到 20% 时约涨 20% 到 40%; 每次回复慢几秒.

### 24.3.8 对方专注 / 睡眠时的消息先存着 (1.0.351)

- 用户发消息时, 如果对方**按人设日程此刻在专注或睡眠** (`other_status()` / `otherStatus()` 的 kind 是 `focus` / `sleep`, 联合行动的同步阶段也算; 没有日程 / 空闲 / 休息 / 吃饭等都不算), OIT **不调用接口**, 把这条消息存着: 消息本来就带发送时间 (每条前面的 `[日期 周几 HH:MM]`), 聊天里照常显示, 状态行写着"专注中 / 睡眠中".
- 记下"存着"的标记 (桌面版 `cfg["retry"] = {hold: true, at, n: 0, since}`, 手机版 `retryN = HOLD_N (-1)`; 同步时都是 `retry:<pid>` 里的 `hold: true`), 跟着聊天对象走, 随设备同步. 存着期间**不会按 10 分钟重试**, 也不会补问 / 追问.
- 对方**第一次空闲 / 休息**时 (状态不再是专注 / 睡眠; 由最后有人操作的设备) OIT 把存着的消息**一次性**发给它: 这些消息合在同一轮用户消息里 (各自带发送时间), 末尾附系统提示"你刚从专注 / 睡眠里出来. 用户在你忙的时候发来了上面的消息 (每条前面写着发送时间), 请现在一次性处理并回复" (kind `retry`, 之后的联合行动 / 网络申请等规则和普通回复一样).
- 等回复的时候对方进了专注, 用户又发了一条: 尚未发出的旧回复取消，新消息存着，等对方空闲 / 休息时一起改写；旧请求被拒绝时也保持存着 (不改成 10 分钟后重试). 清空聊天 / 换设备收到对方的新回复 = 存着的作废.
- 前置 prompt 第 II 条 (专注 / 睡眠时返回 `[refuse to reply]`, 到空闲时一次性处理) 保留, 作为对方比日程晚进入专注 (最多 5 分钟) 时的后备.
- 日志: comm.log 里有 `HOLD 对方在专注中 / 睡眠中: …` 和 `HOLD 对方空闲 / 休息了: …`.

### 24.3.9 对方专注期间发的消息推迟到空闲 / 休息再发 (1.0.383)

- 对方发出一条消息 (回复 / 追问 / 主动消息, 任何一种) 的时候, 如果**按人设日程对方此刻在专注** (`ai_free_at()` / `aiFreeAt()`; 联合行动的同步阶段不算, 没有日程 / 空闲 / 休息 / 睡眠 / 吃饭等也不算), 这条消息**不马上显示**: 记成"推迟" (消息里 `late: true`, `hold: true`, `due` = 对方下一个空闲 / 休息开始的时刻; 专注后面如果接着睡眠, 睡眠也跳过, 一直找到第一个不是专注 / 睡眠的段; 找不到或超过 24 小时就不推迟).
- 到点 (`due`, 和打字延时用同一套"藏着 + 到点显示"; 用户自己不能用沟通时还要等到能用) 才显示: 发送时间 (`at`) **改成那个时刻** (不是实际显示的那一秒; 程序关着错过了也是这个时刻), 排到聊天的最后 (`ts` 重新盖, 所以别的设备收到的顺序也是这样), 未读 +1, 提示音规则同普通消息. 推迟期间不同步给别的设备 (和打字延时一样), 同一段专注里连着发的几条同一时刻一起出来, 保持顺序.
- 推迟的回复算"回复过了" (`unanswered()` 不再为真), 所以不会触发 10 分钟重试; 对方主动消息的 II / III (在空闲 / 休息段开始前 1~3 分钟发) 正好落在专注里, 现在就是推迟到那一段开始时显示.
- 联合行动 (24.9) 的同步阶段是跟着用户走的, 不算对方在专注, 联合行动里的回应照常显示; 合约结束后如果对方回到日程里的专注, 那之后发的话照常推迟.
- **推迟是否继续, 每秒按对方"现在界面上显示的状态"重新判断** (1.0.406): 推迟的消息在对方专注期间 (按日程) 排好了 `due`, 但之后合约 / 联合行动让对方的状态变了 (界面显示休息 / 空闲了), 就**不再等原来日程的那个时刻**, 马上显示, 发送时间改成这一刻 (`min(due, 现在)`); 合约里对方跟着用户专注 / 睡眠时仍然藏着。(1.0.405 以前: 消息一直等到原日程的休息开始才出来, 界面早就显示休息了。)
- 日志: 没有单独的日志; 消息显示出来的时候和普通消息一样。

### 24.3.10 Claudia 的消息自动换成半角符号 (1.0.408)

- **条件**: 聊天对象的人设名字是 `Claudia` (文件名去掉后缀, 不分大小写: `Claudia.txt` / `claudia.md`; `Claudia_background.txt` 这类配套文件不是人设, 不算). 满足时, 对方回复里**显示给用户的那条消息**在 `clean_reply` 去掉 `[]` 之后, 把全角符号换成半角符号; 正在聊的对象和别的对象主动发来的消息都算, 普通回复 / 追问 / 主动消息 / 告白都走这里.
- **换哪些**: 全角 ASCII (`！＂＃…～`, U+FF01–FF5E) 按码位换成对应的半角字符; 全角空格 `　` 换成半角空格; 中文标点按表换: `。`→`.`, `、`→`,`, `，`→`,`, `：`→`:`, `；`→`;`, `？`→`?`, `！`→`!`, `（）`→`()`, `“”` / `「」` / `『』`→`"` / `'`, `《》` / `〈〉`→`<>`, `【】` / `〔〕`→`[]`, `……`→`...`, `——`→`--`, `～`→`~` 等 (`comm.HALFWIDTH_SYMBOLS` / `CommText.HALFWIDTH_SYMBOLS`).
- **只改显示 / 记录的文字**: 记录里给模型看的那份 (`api`) 保留原文 (和 `[]` 标记的处理一样), 用户自己发的消息不动; 半角化之后的文字才进聊天记录、算未读 / 同步给别人, 所以两台设备看到的一样.
- **人设不再要求模型写半角**: 默认 Claudia 的 【说话方式】里"只使用半角符号"那一行和【特别强调】第 1 条删掉了 (1.0.408), 由 OIT 统一转换; 用户自己改过的 Claudia 也会被转 (只按名字判断, 不看人设内容).
- 自检: `python -m comm` (`to_halfwidth` / `is_claudia` + 经由 `_finish` 显示一条全角回复), 手机 `CommTest.claudiaHalfwidth`.

### 24.4 主动发消息

系统会在四种时机让对方主动发一条消息 (都只在**对方可以主动发消息**的时候: 用户休息 / 空闲 / 专注 / 睡眠; 用户外出时不发, 空闲额度用完时也不发. 用户专注 / 睡眠时发出的消息先藏起来, 24.2.3):

- **I. 对方自己的空闲 / 休息段**: 对方正处在人设日程的一段**空闲 / 休息**里, 而且这一段**还剩 10 分钟以上**时, 在段**开始后 1~3 分钟**(随机)按**长时间休息发起谈话概率** (默认 **70%**, 人设里写, 见下) 发一条; 每一段只处理一次 (不管发没发). 对方处在专注 / 睡眠段里时没有这个时机.
- **II. 人设日程里的"空闲"段**: 人设 prompt 里形如 `12:30-13:00:空闲` 的行(每天重复), 每一段**开始前 1~3 分钟**(随机), 有人设里写的概率发一条 (默认 **80%**).
- **III. 人设日程里的"休息"段**: 由循环段 `[循环 …]` 生成的每一段休息 (1.0.308 起休息只能由循环生成, 不能再逐段写 `8:40-9:18:休息`), 每一段**开始前 1~3 分钟**, 有人设里写的概率发一条 (默认 **60%**).
- **IV. 人设日程里的"睡眠"段**: 形如 `23:30-6:30:睡眠` 的行, 每一段**开始后 5 分钟**, 有人设里写的概率发一条 (默认 **60%**, 人设里写 `睡眠发起谈话概率:40%`). 这是睡眠期间唯一的一条: 发完对方继续睡, 用户回复时对方按日程拒绝继续聊; 系统提示里**不再**有"以晚安开头"之类对具体人设的要求 (1.0.334 起不写进代码): 内置 Claudia 的人设文本里自己写了一行"睡眠段开始后的那条主动消息……以'晚安'开头", 别的人设想要就在自己的提示词里写; 没有写睡眠段的人设没有这个时机.
  - 日程行的写法: `H:MM-H:MM:名字`(可以缩进, 可以以 `-` / `*` 开头; 冒号可以是全角; 连接符 `-` `–` `—` `~` `至` `到` 都行); 名字里有"空闲"(或 idle / free)算空闲段, 有"睡眠"(或 sleep, 含"睡觉"等带"睡"的名字)算睡眠段; **专注 / 休息只能用循环段写 (1.0.308 起)**: 逐段写的 `8:00-9:00:专注` / `8:40-9:18:休息` (中英文都一样) **不再被认出来, 直接忽略** (写了也不会触发主动消息, 状态里也看不到); "不休息" / "不专注"之类不算;
    英文写法不分大小写 (`12:30-13:00:Idle` / `[loop 7:00-12:00]` 都行). **其他名字的段 (午饭 / 晚饭 / 上课 …) 一律算空闲段**: 也会按空闲触发主动消息 (I / II), 聊天页的状态也按空闲显示 (修饰不影响); 只有"不休息" / "不专注"这类否定写法不算, 空名字的段也不算. 没有按这个格式写的人设(没有日程), 就没有 I / II / III / IV 任何一种时机. 只认段的**开始时刻**, 跨零点的段也行(23:59 能看到 0:00 开始的那段).
  - **专注段不触发主动消息**: 只用来在聊天页显示对方的状态 (24.3.2, 24.2.3); 睡眠段只在开始后 5 分钟发那一条 (IV), 其他时间按睡眠处理, 也没有 I.
  - **标准写法写在人设 README 里**(人设文件夹里的 README.md / 设置里的"写法"; 跟随界面语言, 电脑 / 手机各写各的): 专注和休息只写循环 `[循环 7:00-12:00][100min]` (逐段写的 `7:00-8:40:专注` / `8:40-9:18:休息` 认不出来, README 里也这么写); 循环以外的时间段每段单独一行 `开始-结束:名字`, 例如 `12:30-13:00:空闲`、`23:30-6:30:睡眠`;
    也可以用英文名字 (`12:30-13:00:Idle`、`23:30-6:30:Sleep`、`[Loop 7:00-12:00][100min]`). **标准格式后面可以加修饰来限定具体活动**, 例如 `12:30-13:00:空闲(午饭)`; 修饰只是说明, 不影响这是哪一段, 也**不会显示在聊天页的状态里**; 格式和名字要和标准用语一致才能被认出来.
     **循环段**: `[循环 HH:MM-HH:MM][Nmin]` (英文 `[Loop ...]` / `[Cycle ...]` / `[Repeat ...]`, 不分大小写; N 是每次专注的分钟数, 不写 `[Nmin]` 默认 **100min**), OIT 按 **N 分钟专注 + F(N) 分钟休息**交替生成到这段结束 (最后一段按结束时刻截断, F 就是上面的专注-休息函数); 例如 `[循环 7:00-12:00][100min]`. **循环总是自动生成** (1.0.308 起专注 / 休息只能写成循环段; 循环的时间范围里别的段 (空闲 / 睡眠 / 吃饭) 照样生效, 但最好别写在里面; 重复写的同一个循环只算一个); 生成发生在每次读取人设时 (打开 OIT / 新对话 / 换人设, 人设文件改动后也会重新读取).
  - **读取时机**: 每次**打开 OIT**、**开始新对话**(清空聊天记录, 或另一台设备清空同步过来)、**换人设**时, OIT 都重新读取人设并按里面的日程调整这些时刻 (循环段也在这时重新生成); 人设文件改了之后(修改时间 / 大小变了)也会自动重读, 不用重启. 每次读取在 `comm.log` 里记一行 `SCHEDULE …: 空闲 N 段, 休息 M 段, 专注 K 段, 睡眠 L 段`(不记人设内容), 没认出日程时可以看这行.
  - **概率写在人设 prompt 里** (1.0.275 起, 设置里的"主动发消息"调整项和设备同步都去掉了; 1.0.286 起 I 也有概率), 各占一行, 冒号中英文都行:
    `长时间休息发起谈话概率:40%` (I: 对方自己闲着、这段还剩 10 分钟以上时那一条, 默认 70%) / `空闲发起谈话概率:50%` (II, 默认 80%) / `休息发起谈话概率:40%` (III, 默认 60%) / `睡眠发起谈话概率:40%` (IV, 默认 60%);
    `空闲发起谈话概率:50%` / `休息发起谈话概率:0.4` (`n%` 或者小数; 不带 % 的数字大于 1 就当百分数; 超出 0~100 截到范围内; 同一种写了几行只认第一行; 没写 / 写错了用默认 80% / 60% / 60%).
    人设文件改了自动重新读取; 人设文件本身每 2 分钟在绑定的设备之间同步一次 (24.6), 不用自己保证两台一致. 自带的 Claudia 写的是 空闲 20% / 休息 20% / 长时间休息 20% / 睡眠 40%, Assistant 都是 0% (`personas/Claudia.txt`、`personas/Assistant.txt`, 嵌在 `comm/` / `Comm.kt` 里的副本要同步; 用户自己文件夹里的同名文件不会被覆盖).
  - I 触发时, 系统消息说明"按你的日程, 你现在有空 (这段还剩约 N 分钟)", 允许主动发一条 (不要透露日程); II / III / IV 触发时, 发给对方的系统消息说明"你的空闲 / 休息时间将在 HH:MM 开始 / 你进入睡眠约 5 分钟了, 即使此刻处在专注或睡眠时段也允许主动发一条(不要透露日程)", 免得对方按日程回 `[refuse to reply]`.
- **每个时间点只处理一次**(不管发没发; 概率按这个时间点定下来, 重开程序不会重新摇): 对方日程段的开始时刻 (I / II / III) 和睡眠段的开始时刻 (IV) 记在聊天记录旁(随设备同步, 最近 12 个), 到点后超过 2 分钟才发现(程序刚打开)的不补发.
- **爆发后睡后必谈**：特殊空闲一旦触发爆发，即记录原段结束时刻为 `burst_sleep_after`，之后下一段睡眠开始 5 分钟时必定触发 IV 类消息；普通概率（含 0%）、最近 10 分钟聊天和迟到 2 分钟限制均不阻止，未触发爆发则沿用原概率。静音、切断、联合行动、主端、额度、用户外出和模型可用性等外层限制保留；限制解除且仍在该段睡眠时补触发。待触发边界与 IV 类去重键随对象保存和同步，固定钟点、持续时间日程及跨午夜一致，前后台均适用；发出后清除待触发边界，相同睡眠段不额外再发普通 IV 消息，清空聊天一并删除。若睡眠紧接特殊空闲，消息请求仍处于额外 10 分钟的爆发档位；推迟到爆发结束后发出的消息按当时状态回复。
- **爆发次日早间必谈**：若该对象昨天（本地日历日）触发过张力爆发，今天 06:00（含）–12:00（不含）内首次可主动发消息且对方处于日程空闲 / 休息时，必定触发一条主动谈话；持续时间日程的睡眠延迟空档不算。包含有名字的空闲活动及特殊空闲，不要求剩余 10 分钟，也不受概率（包括 0%）、迟到 2 分钟和近期 10 分钟谈话间隔限制。先执行此规则，再判断常规主动消息及主动告白；同段的 I 类主动消息同时记为已处理。静音、切断、联合行动（当前对象）、用户外出、额度、主端和模型可用性限制仍有效，恢复后若仍在当日早间空闲 / 休息可触发。每天每对象仅触发一次，触发日期随对象保存、同步，重启不重发；无早间空闲不顺延到下午或后天。前后台对象一致；仍使用主动消息语言设置及拒绝后再请求一次的流程。
- **两条主动消息之间至少隔 10 分钟**: 相邻的日程段(例如 22:58 休息、23:00 空闲)、或同一段里 I 紧接着 II, 后一个时间点算处理过但不发.
- 对方可以拒绝(`[refuse to reply]`), 那就什么也不显示.
- 不在聊天页时收到对方的消息, 侧边栏"💬 沟通"后面显示 ●, 并响一声 (见下面的提示音).
- **提示音** (1.0.413): **只要用户不在沟通页面**, 收到任何新消息 (主动消息 / 回复 / 追问 / 其他对象的) 都播一声柔和的提示音 (两个轻轻的钟声, 慢起音、渐弱, 音量比整点提示音小得多; 电脑 `comm_ping.wav` 在数据文件夹, 手机走通知音量). 在沟通页面上看着就不响; 已经进入专注 / 睡眠 / 外出, 不能用沟通了, 也不响. 以前只有主动消息、并且前 5 分钟没聊过才响 (更早的规则), 1.0.413 起改成这样.
  别的设备收到的消息同步过来时这边也响一声 (同样只看在不在沟通页面). **专注 / 睡眠时对方发来的消息先藏起来, 不响; 回到休息 / 空闲显示时才响** (24.2.3).

### 24.4.1 非正在聊天的对象也会主动发 (1.0.279)

- 以前只有**现在聊的这个对象**会按它的人设日程主动发消息 / 追问 (24.3.5); 切到别人之后, 其他人就不会再来找你了. 现在**聊过天的其他对象**照样会 (各按各的人设日程和 `空闲发起谈话概率` / `休息发起谈话概率`, 各自记各自"已经处理过的时间点"),
  新消息记进它们各自的聊天记录, 导航栏的 ● 亮, 不在沟通页面的话响提示音, 切过去就能看到. 只有**主端设备** (24.6) 发请求; 没聊过天的人设 (只是切换时留下的空记录) 不会来找你.
- **一个一个来**: 非正在聊天的对象的请求同时最多一个, 两次之间至少隔 2 分钟 (`BG_STAGGER`); 它们的请求只有一次调用 (没有要资料的轮次), 回复了 `[refuse to reply]` 或去掉 `[]` 之后什么也没剩就不显示. 同样只在**对方可以主动发消息**的时候 (休息 / 空闲 / 专注 / 睡眠) 发; 专注 / 睡眠时收到的也先藏起来, 回到休息 / 空闲再显示.
- **开关** "允许非正在聊天的人发起对话": 设置 → 沟通 → "💬 主动发起" (没有说明文字), **默认开**, 随设备同步. 关了就和以前一样, 只有现在聊的这个对象会主动发.
- **每个对象的"禁止主动发起"**: 聊天页输入框上方的 🔔 / 🔕 按钮 (点一下切换; 🔕 = 禁止): 这个对象不再主动发消息, 也不追问 (不管它是不是正在聊), 随设备同步 (`mute:<对象>`).

### 24.6 设备同步

- **同步的内容**(同步文档 `comm`): **每个聊天对象各自**最近 60 条聊天记录(含附在消息里的数据和系统触发的消息, 键里带对象的编号), 清空的时刻, 主动消息的标记(已经处理过的时间点, 两边合并), 对方不方便时的重试状态; 还有我的身份背景, 主动发消息的概率, **允许非正在聊天的人发起 / 显示头像** 的开关, 以及**每个对象的"禁止主动发起"**(`mute:<对象>`). 单次流式回复不提供分条续发设置。新回复的未发片段仅本机排队，发送后才同步；远端已经发出但本机因沟通限制暂藏的历史仍兼容 `hold` / `due` / `late`。
  **不同步**: API Key / 模型, 人设选择, 头像图片, share data 的开关和进度 (只在本机界面里)。
- **人设文件**: 每 **2 分钟**检查一次本机人设文件夹的变化 (新增 / 改过 / 删掉), 随同步发给其他设备 (同步文档 `personas`, 键是文件名, 值是全文); 对方发来的也并进来, 后改的为准, 删除也同步. 现在选着的人设被改 / 删后马上重新读日程. `README.md` 不同步 (各设备按界面语言自己生成). 第一次绑定时子端用母端的人设 (子端多出来的会被删掉).
- **合并**: 每条消息有自己的编号 (时间 + 设备) 和时间, 两台设备的记录按时间合在一起, 同一条只留一份; 掉出最近 60 条窗口不算删除。收到对方的 AI 消息时, 不在聊天页的设备也显示 ●。
- **主端 = 最晚的一条消息是哪台设备写的**(用户在那台上发的, 或那台上 AI 回复的): **只有主端调用 AI、主动发消息、重试**, 回复同步给其他设备; 所以同一条消息不会被两台设备各问一遍, 同一段空闲也只有主端发一条主动消息。
  在另一台设备上发消息, 那一台马上成为主端。还没有消息时, 或者主端设备不在线时, 由最后有人操作的设备代为处理。
  自由学习外出时, 外出设备是聊天主端; 家中设备即使联网也不替它调用 API。外出设备回来后的第一次同步, 外出时间内由其他设备生成的旧 API 回复会丢弃, 外出设备实际聊天记录优先, 防止较晚的家中时间戳覆盖真实对话。
- **清空**(按钮或 `/clear`)一台做, 另一台也清空(清空时刻之前的记录同步回来也不会复活)。
- 发送 / 收到回复 / 清空之后马上同步一次, 不等下一轮。
- 收到新消息时, 聊天页自动滑到最新一条 (正在往上翻看很早以前的记录时不打断)。
- **联合行动** (24.9) 随设备同步 (同步文档 `comm` 的 `joint` 键: 整个联合行动的状态, 带最后改动的时刻 `ts`, 后改的为准; 清空聊天 = 联合行动作废); **选好、还没发出去的**联合行动和 📎 选好的附加数据一样不同步。

### 24.7 聊天框上方的按钮和帮助 (1.0.308)

- 聊天框上方有功能按钮，包括帮助、阅读、share data、主动发起开关、联合行动、识字、图片附件与共时闹钟；阅读可选择自己阅读或发起 coread（24.22）。选好的联合行动 / 📎 数据显示在按钮旁边 (手机在按钮下面一行), 带 ✕ 可以取消。
- **❓ 帮助** 弹出一个说明窗口 (跟随界面语言), 逐个解释这几个按钮的作用, 最后用醒目的颜色**特别提醒: 合约词条"无言为真"生效时会禁止"沟通"的使用** (不能发消息, 对方的消息也收不到, 合约结束后才能恢复, 24.3.3)。 (1.0.407: 窗口分**左右两栏**, 每个按钮的说明精简成一两句, 左栏先排满再排第二栏; 手机上也是两栏.)

### 24.14 图片消息与识字 (聊天框上方的 📎 / 🖼)

- 📎 可从文件选择图片；桌面 Ctrl+V 支持剪贴板图片或复制的图片文件，手机使用系统图片选择器并与输入文字一起发送。图片本身不进入文字聊天存档或设备同步，只在该轮请求中作为多模态内容发出；支持 PNG/JPG/WEBP/GIF，最大 4.5 MB。图片始终交给当前聊天模型；聊天模型调用 `oit_subject` 时，教育子代理可以接收同一张当前图片和题目，但不接收完整聊天历史。
- 🖼 识字单独调用选定的 OCR 配置，不带人设或聊天历史，结果放回输入框供用户编辑。

### 24.14.1 演奏评判

- 桌面沟通页提供「演奏评判」左右两栏。左侧选参考 MIDI 或乐谱图片/PDF，右侧选演奏 MIDI、钢琴音频，或录制 USB、驱动及蓝牙 MIDI 输入。手机沟通页可选择 MIDI、MusicXML / MXL 或当前选曲作为参考，选择 MIDI / 音频文件或录制 USB、蓝牙 MIDI 输入；不提供图片和 PDF 识谱。点开始录制后以首个力度大于零的按键为零点，保留松键与延音踏板，手动停止后可开始评判。录制只在本机当前评判窗口使用。评判完成后先暂存为 `🎼 演奏评判` 附件，随下一条用户消息提交；评判提示与摘要放在该消息正文之前，不会自动发送。
- 两端按参考谱和演奏各自的首音对齐后比较。这会消除开头的等待，但无法识别从曲中哪个小节开始，也不会跳过误弹的起始音。摘要含命中 / 漏音 / 多音、起音及时值误差和演奏时长，不上传原始媒体。PC 使用 Partitura；安卓运行 Kotlin MIDI 分析。
- 摘要由独立评判子代理生成自然语言建议，并为同一曲目保留最近五次评判上下文，再与建议及结构化差异一起交给聊天模型。未配置评判模型时跟随当前聊天配置。聊天模型可结合速度比例、起音与时值误差、漏音 / 多音分布等信息判断是否存在有依据的演奏意图；只有模式连贯且能与偶发失误区分时才提及，证据不足时不推测。回复最早显示时间从评判消息送出时计算，为 60 秒 + 演奏时长，并随设备同步。

### 24.14.3 本地乐谱曲库与AI选曲

- 默认曲库仅供 Claudia 使用，其他人设初始曲库为空。两端均只向 AI 返回当前人设的曲目；曲库不在 UI 展示，也没有编辑、删除或改配入口。新增曲目只能由用户上传，归上传时选中的人设，其他人设不可查询、选择或生成。Windows 在设置 → 额外功能上传，Android 在沟通工具栏使用乐谱按钮上传。支持 MuseScore MSCX / MSCZ 和 MusicXML / MXL，单文件上限 50 MiB。
- 两端默认资源位于 `music_library/defaults/`；上传位于 `music_library/uploads/<人设文件名SHA256前20位>/`，选曲按人设独立保存。旧版共享上传与选曲保留给 Claudia。曲目文件、归属和选曲仅在本机保存，不随聊天同步。
- AI 先用 `oit_music_catalog` 浏览最多 80 首，再用 `oit_music_select` 提交曲目编号。选择作为主线程待提交动作，在最终回复通过校验并成功提交时保存；AI 可据曲名、作曲家和标签判断是否适合当前语境。选曲只记录当前曲目，不代表已经播放。
- 用户明确要求演奏曲名明确但不在当前曲库的曲目时，AI 可在 `oit_reply` 同时申请 3 分钟联网并设置 `network_now=true`，跳过普通申请的 2 分钟等待；联网额度和既有申请、联网中或冷却状态仍有效。联网搜索最多持续 3 分钟；找到可确认的合法乐谱来源后请用户导入，不直接下载或加入本机曲库。3 分钟内找不到则结束搜索并请用户提供乐谱。模糊曲名或仅要求选曲不触发搜索。
- 33首常驻曲目包含舒曼《童年情景》13首、德彪西《贝加莫组曲》4首、柴可夫斯基《四季》3首，以及格里格《抒情小品》7首、莫扎特钢琴奏鸣曲乐章4首、李斯特《巡礼之年》5首和勃拉姆斯《摇篮曲》1首。另有格里格《Erotikk》和李斯特三首彼特拉克十四行诗，共4首亲密主题曲目。DCMLab 曲目来自对应曲集固定 Git 提交的校对谱，采用 CC BY-NC-SA 4.0；勃拉姆斯曲目来自 OpenScore Lieder 固定 Git 提交，采用 CC0 1.0；来源、许可和 SHA-256 记录在 `defaults/music_library/catalog.json`，上游许可文件随资源保存。
- 4首亲密主题曲目只属于 Claudia；只有 OIT 已记录亲密关系且当前 Valence ≥ 70 时才会出现在曲库。目录、选曲、MIDI 生成和演奏准备都会复核条件，实际播放时再次检查；关系未确立、Valence 低于门槛或使用其他人设时，直接传曲目编号也不可访问。Valence 回落后，之前保存的受限选曲也不能继续使用。
- 应用数据重置会删除所有人设的上传曲目和选曲状态；重新初始化时仅 Claudia 恢复内置曲库，其他人设为空。清空某个聊天不会删本机曲库。
- 用户可以说“弹一首安静的曲子”“演奏梦幻曲”或“再弹一次”。模型查询当前人设可用曲库、选曲并调用 `oit_music_perform`。PC 用 MuseScore 导出人性化 MIDI 并渲染 MP3；安卓内置曲目使用预生成 MIDI，用户上传的 MusicXML / MXL 用 Verovio 转换；两端均由本机合成器输出音频。音频准备好且正式回复真正显示后才播放，打字延迟或隐藏期间不播放。曲目 MIDI 与音频缓存在 `music_library/generated/`，缓存签名包含源文件、算法及本机音色库；更新或损坏时重新生成。安卓不直接转换用户上传的 MSCX / MSCZ 文件。
- 演奏仅限用户空闲或休息；Claudia 还要求当前 Valence ≥ 30，准备演奏与实际播放时都会检查。播放时持续复核状态，进入专注、睡眠、外出或硬性沟通限制时停止。实际 MP3 播放期间，用户发出文字或离开沟通页面会触发 Claudia 的 `music_discourtesy` 负向效价条件；准备阶段不触发。离页事件在因离页停播前检测。用户说“停止演奏”时通过 `oit_music_stop` 停止播放并取消排队；新演奏替换上一首，切换人设、离开沟通页、清空聊天、重置和退出同样停止。待播动作只保存在本机会话内存，不写聊天存档或同步，不因重启重播。安卓端可浏览、导入和选择，演奏工具会明确返回当前不支持，不能冒充播放成功。
- Windows 的「设置 → 额外功能 → 导出所选曲目为 MIDI」和 `oit_music_generate_midi` 共用 MuseScore 演奏转换器。安卓内置曲目从随包精确 MIDI 生成演奏副本，MusicXML 使用 Verovio 转换；两者都应用保守人性化处理。保留音高、速度、踏板和鼓通道，不加错音或漏音；依据、参数和限制见 [数据考察](../research/midi-humanization.md)。演奏 MIDI 按源文件与算法签名缓存，有效缓存不重复随机。

### 24.14.2 识别字体 (聊天框上方的 🖼, 1.0.395)

- **用途**: 用户选一张图片, OIT 让独立 OCR 模型把图片上的文字读出来, **放进聊天框** (接在已有内容后面, 另起一行; 用户可以再改, 再自己发送). OCR 图片不会存下来或进聊天记录；用户也可以用 📎 将图片本身发给聊天 AI.
- **怎么做**: 一次单独的请求 (不带人设, 不带聊天记录, 不开思考, temperature 0): 系统提示 `ai_assist.OCR_SYSTEM` 要求"原样提取文字, 保持语言 / 顺序 / 换行, 不翻译不总结不解释, 看不清的字用 ?, 没有文字只回复 [no text]". 图片作为 base64 放在这条用户消息里 (Anthropic 协议: `image` + `source`; OpenAI 兼容: `image_url` + `data:` 地址)，默认用当前聊天模型，也可在 AI 模型设置里单独分配识字配置。
- **限制**: 只收 PNG / JPG / WEBP / GIF (看文件头, 不看扩展名), 图片文件最大 **4.5 MB** (`OCR_MAX_BYTES`). 电脑上超过就提示"图片太大了"; 手机上太大或格式不认 (BMP / HEIC …) 的先解码、缩到长边 2400 像素以内、重新压成 JPEG 再发. 没有识别到文字 (`[no text]`) 提示"图片上没有识别到文字", 不改聊天框.
- **其他**: 识别进行中按钮变成 "…" 不能再点; 请求日志 comm.log 里记 `OCR start / ok / FAIL` (不记内容); 不占沟通的每天空闲时间, 也不受对方 `[cut off]` 的限制 (它不是在和对方聊天), 但"无言为真"会让整个沟通页不能用. 代码: `comm.Comm.ocr_image` / `Comm.ocrImage`, `ai_assist.ocr_image` / `Ai.imageLocal` (请求线程里的"下一次请求带这张图").

### 24.11 日程文件 routine (1.0.355)

- **特殊空闲固定半小时**：双端统一使用 `COMM_SPECIAL_MINUTES=30`。持续时间模板里的特殊空闲无论声明多少分钟，实际都按 30 分钟累计后续边界；前一循环的末尾休息不再应用延后波动，不得挤占特殊空闲。前一循环休息的提前、延后波动均不生效；起床后首段就是特殊空闲时，起床也不应用波动，避免改变该段长度；循环内部专注波动不移动其起止边界；默认 Claudia 未平移时固定 23:00–23:30，平移后整体移动、允许跨午夜，最后一项结束立即睡眠。旧固定钟点日程也按起点加 30 分钟确定终点，重叠的普通活动、睡眠或循环部分让出该时段，保留其余部分；超出半小时的旧声明不会延长特殊空闲。所有状态、主动消息、爆发与睡后消息均读取同一实际日程。

- **配套文件 (1.0.366 起不止日程)**: 人设 `X.txt` 旁边的 `X_名字.txt` (名字任意, 同文件夹里真的有 `X.txt` / `X.md` 才算; 有好几个可能的 X 时取最长的; 没有 X 的 `X_名字.txt` 是普通人设) 都是 X 的配套文件: 不出现在人设列表里; 发给模型前按文件名顺序 (不分大小写) 和 `X.txt` 合并成一份 (`read_persona_full` / `readPersonaFull`, 中间空一行), 所以 `X_background.txt` 在 `X_templates.txt` 前面; 改任何一个配套文件都会重新读日程 / 弹"修改人设"; 日程引擎优先读取 `X_templates.txt`，兼容旧 `X_routine.txt`. 默认人设 = `Claudia.txt` + `Claudia_background.txt` (身份背景: 创伤 / 学习目的 / 音乐 / 英语 / 阅读等话题的回答依据) + `Claudia_example.txt` (对话范例) + `Claudia_templates.txt` 四个文件; 范例文件在首次安装或升级时补齐, 用户修改后不覆盖. 背景文件的升级规则和日程文件一样 (`background_base`). 下面写的 `X_templates.txt` 特有规则:
- **统一模板文件**: 人设 `X.txt` 旁边的 `X_templates.txt` 集中存放日程、数据生成、张力增长与关系条件模板: 不出现在人设列表里; 内容拼在人设后面一起发给模型; 随设备同步; 手动改它同样弹"修改人设会清除聊天数据" (清的是 X 的聊天). 默认人设是 `Claudia.txt` + `Claudia_templates.txt` (一起内置, 没改过的旧 Claudia 升级时一起换成新版). **日程文件自己升级, 不看 `Claudia.txt` 有没有被改过** (每次启动检查): `Claudia_templates.txt` 缺 / 空白 → 补上当前内置版本; 内容是更早的内置版本 (没改过) → 换成当前版本; 用户改过的不动; `Claudia.txt` 不在时不补 (不然它会被当成人设). 补上 / 换掉之后同时更新备份, 不弹"修改人设". **"没改过"的判断** (`Claudia.txt` 和日程文件一样): 文件内容是任一版更早的内置版本 (升级链), **或者是 OIT 上一次见到的内置版本** (`comm_config.json` 的 `claudia_base` / `routine_base`: 每次启动时文件等于当前内置版本就记下它的校验值). 所以用户改了人设、弹窗点了"确定" (保留修改) 之后又改回原样, 下次更新照样换成新版; 也不用每个旧版本都进升级链.
- 没有日程文件的人设走原来的"每天重复的钟点"日程 (24.4); 有日程文件的人设里旧的钟点写法不再读.
- **旧文件迁移**：启动时将 `X_routine.txt` / `.md` 原样改名为 `X_templates.txt` / `.md`，备份一起更名，不清聊天；已有新文件时不覆盖旧文件。Claudia 主文件中的完整条件区块在新模板没有对应区块时移入其中，保留自定义数值，写入成功后再删主文件中的区块。未改过的内置内容通过原有 CRC 规则升级到完整默认模板；用户修改过的内容保留。两个名称同时存在时，日程和合并发给模型的上下文均优先采用新模板，不重复加入旧文件；旧设备同步来的旧文件仍可保存，但不会覆盖新模板。同步仍按原文件通道，备份与聊天清空判定不变，配置键 `routine_base` 和旧 API 名称保留兼容。
- **按持续时间算日程** (`routine/`): `初始起点:6:30` 是起床的基准时刻; 之后每项活动一项接一项: `30min:洗漱,吃早饭` (持续时间:名字; 名字不是"空闲"的是有名字的活动, 联合行动的开始时间不会和它重合, 在状态里算空闲), `[循环 300min][100min]` (总长 300min, 每轮专注 100min + 休息 F(100); 也可以写 `5h`). **循环总以休息结束** (1.0.400 起不再把最后一轮直接截断): 满轮 (专注 N + 休息 F(N)) 能排几轮排几轮, 剩下的时间 R 做**最后一轮**: 专注提前结束, **休息按这一轮实际的专注长度重新算** (解 f + F(f) = R, 休息取整分钟 (至少 1 分钟), 专注 = R − 休息), 让这次休息的末尾正好对上循环的末尾 (例: 300min / 100min → 专注 100·100·19, 休息 38·38·5; 240min / 50min → 专注 50·50·50·32, 休息 16·16·16·10). 剩下的时间太短 (最后一轮专注不到 1 分钟) 并进上一次休息; 总长连一轮都排不了 (约 2 分钟以内) 退回只有一段专注 (`routine.loop_pieces` / `Routine.loopPieces`). **固定结束边界**：以当天初始起点（含已生效平移）累计各项持续时间，空闲、重要活动与特殊空闲的结束时刻固定；连续的午饭 / 空闲、晚饭 / 空闲按文件顺序衔接，最后一段结束立即开始专注。最后一项结束立即进入睡眠。内置 Claudia 未平移时，早间活动固定 7:00 结束，午饭及其后空闲固定 13:00 结束，晚饭及其后空闲固定 19:00 结束，特殊空闲固定 23:30 结束；平移后这些边界整体平移，允许跨午夜。
- **每天的波动** (分钟, 整数, 两端都可能取到; 由 人设 + 日期 决定, sha256, 同一天所有设备算出来一样):
  - 睡眠结束时间波动 `[-5,0]`: 当天的起床时刻 = 初始起点 + 波动, **只改变第一段活动的实际时长，不平移后续结束边界** (内置 Claudia 起床总在 6:25 - 6:30);
  - 下一个专注开始 / 结束节点波动 `[-3,2]` / `[-2,3]`: 循环内部专注的起止各自波动，空闲 / 重要活动后的首段专注起点固定，不应用开始波动。循环内开始提前 → 前一段休息被截短; 开始推后 → 前一段休息变长 (**1.0.441 起循环里不留空档**); 结束提前 / 推后 → 后面的休息变长 / 变短. 联合行动之后重算的循环没有这两项波动;
  - 循环末尾休息结束时间波动 `[0,5]` (1.0.400, 日程文件里的这一行; 没写 = 不晚): **每个循环最后那次休息**的结束比循环的结束晚这么多分钟 (每个循环各抽一次), **只占用下一活动的开头，不移动该活动及后续活动的结束边界**，下一活动至少保留 1 分钟；下一项是特殊空闲时不延后休息，完整保留固定的 30 分钟；后面没有活动时不延长，避免推迟睡眠. 联合行动之后重算的循环以 (推后的) 循环结束为准, 没有这项波动;
  - 睡眠开始时间波动字段继续兼容解析，但不再影响日程：最后一项结束立即睡眠，不追加延迟空闲。睡眠开始后 5 分钟的主动消息 (24.4 IV) 按固定的实际睡眠起点计算。
- 状态 (聊天页顶上、专注 / 睡眠时存消息、思考判断) 都按这份当天算出的日程; 空闲段 / 休息段的主动消息 (24.4 I~III) 同样, 睡眠被延迟的空档不触发 II / III. 联合行动结束后休息结束的时刻落在循环里 → 从那一刻**立即开始专注**到循环结束, 落在吃饭 / 睡眠 / 空闲里不影响.
- **给模型的实时状态**: 每次请求, 最后一条用户消息后面贴一段 (用户看不到, 不写进聊天记录): 此刻的状态 + 从几点开始 + 已经多久 + 所在循环的开始时间和每轮专注时间 + 下一段专注 / 睡眠 5 分钟内开始的话提前说一声. 模型以此为准, 不要自己推算.
- **Claudia 的合约休息奖励**：自主完成的合约按实际词条计算奖励秒数，记录与日程共用同一笔到账事件。一般在循环内休息结束时使用奖励延后下一段专注，不能延后循环中的首段专注；从延后时刻重新按专注与休息交替推算到固定的循环结束时刻。最多填到循环结束，不挤占午饭、空闲、特殊空闲或睡眠；完成奖励填满循环后，尚未用掉的奖励按 ×0.85 结转，只在填满时扣一次，下一循环首段专注照常开始，结转用于延长第一次休息。循环外到账的奖励同样留待下一循环。
- **Claudia 接续联合行动后的休息**：用户发起的联合行动无论完成或失败，先保留合约结束时尚未走完的共同休息；该段走完或被用户提前结束后，Claudia 立即用自己的剩余休息接续，无需等下一次普通休息，不再等待用户之后发起的奖励休息。例：10:00 合约结束、共同休息到 10:30，另得奖励 30 分钟，则 10:30–11:00 接续休息，再从 11:00 重算余下循环。11:40 失败、无共同休息、剩 25 分钟，则用 20 分钟填到 12:00 循环结束，正常进入空闲，余下 5 分钟原样留给下一循环第一次休息；失败结算的这次接续不套用完成奖励的 ×0.85。联合行动期间不消费独立奖励；结算事件及共同休息结束边界随 `comm.joint` 保存与同步，重启或切换设备不重复发奖。其他人设及旧版已结束的联合行动继续使用原有同步休息规则。
- **对方自己的 OIT 数据** (对方查询 `[timer]` `[log]` `[calendar]` `[stats]` `[net]` 时得到的是这些, 不再是空白模板; `[contract]` `[rules]` `[settings]` `[reset]` `[prescript]` 仍然是模板). 都是**实时算**的, 只有已经发生的部分:
  - 计时器: 今天每一段专注 / 休息 / 睡眠 (正在进行的写 `HH:MM-现在`), 目前状态, 剩余休息, 今日总专注, 这一轮专注;
  - 整点记录: 只给**已经结束**的格子 (没结束的这一小时不给); 睡着的格子照 OIT 自己的整点记录 (8.2) 填 `睡眠` (睡眠占了这一格一半以上, 一小时 = 30 分钟以上; 半小时的格子 = 15 分钟以上; 1.0.368 起, 以前这些格子是空的, 不出现在记录和统计里; 旧存档里的空格子下次补数据时重新算). 专注为主的格子从 `整点记录专注填写列表` 抽, 吃饭这类有名字的活动为主的格子写活动名, 其余从 `整点记录休息填写列表` 抽;
  - 列表 `{}`: 没写概率的项**平分**其他项剩下的概率; `X%:聊天` 的 X 随用户在**这一格**里发的消息数变: 0 条 0%, >= 20 条 50%, 中间均匀分配 (细化规范时格子是半小时, 阈值按比例减半: >= 10 条 50%);
  - 标了 `(基准数据)` 的列表, **每一项**的概率每天按 `[-2%, 2%]` 的比例波动 (加起来本来是 100% 的归一回 100%);
  - 联网: 总联网时长 = 清醒但不在专注的时间的 1/4, 按 `联网时间理由列表` 分给各个理由; 窗口: 第一台设备用在专注的时间, 其余设备用在休息 / 空闲的时间, 按各自的 `窗口使用时间` 列表分给各程序, 名单没写满 100% 的剩下算"空白";
  - 合约记录 (1.0.356): 和用户**真的一起顺利完成**的联合行动 (state=rest, result=completed) 照实记下来 (用户选的词条, 危机等级, 结束时间; 包括对方平时不选的词条), 排在最前面, 最多留 20 条; 失败 / 提前终止的不记, 同一次只记一条, 哪台设备都能记 (联合行动状态随设备同步). 不够 5 条的用按日程生成的补: 每天约 30% 的概率完成一个合约, 词条随机, 危机等级落在 `合约记录难度` 里, 不碰 `不选择的词条` 和 `违规词条` (整个系列都算; 对方主动发起联合行动时也不选这些词条).
- **数据会保存**: 数据目录里的 `routine_<对象编号>.json` 存实际发生过的时间线 (一段段) 和整点记录的格子; 每 30 秒 / 每次被查询时补到现在. 联合行动期间的时间线按联合行动里的状态记. 好几天没被调用 (程序没开 / 没人查) 时, 缺的部分 (最多补 14 天, 第一次从 7 天前开始) 按日程规则自动补齐; 补的格子里用户发的消息数按聊天记录里还留着的算.

### 24.12 share data (1.0.357)

- **开关**: 沟通页输入框上方的 👀 / 🙈 切换按钮 (和 🔔 / 🔕 一样点一下切换; 👀 = 打开, 🙈 = 关着; 手机同一行). 打开前要能聊天 (选了人设, API 配好); 只存在本机界面, 不存盘, 不同步.
- **用户发起要先争取对方同意 (1.0.384)**: 点 🙈 会先把 share data 请求作为附件加入待发送内容，与联合行动一样由下一条消息带出；附件可以与其他待发项并存，也可在发送前点 ✕ 清除。发送后向人设询问同意: 回复 `answer="yes"` 才真的打开 share data (界面跳到计时器页); `answer="no"` 或未明确同意则不开启，旧方括号回复仍兼容。拒绝 / 没表态 / `[refuse to reply]` (不方便) / 出错 / 超过 5 分钟没回复 / 清空聊天 = 这次请求作废, 弹一条提示 (`对方拒绝了 share data` 等), 不会重试.
  - 暂存请求时检查用户现在能聊天 (`problem()`); 随下一条消息正式发送时还会检查对方不在专注 / 睡眠。等待答复状态只存在本机界面，不存盘、不同步；点 ⏳ 可取消。
  - **对方发 [share data] 邀请, 用户点接受**这条路不变 (邀请本身就是对方的同意, 不再问一次). **邀请 5 分钟没人点接受 / 拒绝 = 自动清理** (1.0.428, `SHARE_INVITE_TTL`): 聊天页的接受 / 拒绝按钮消失, `share_inv` 清空.
  - Claudia 的设定 (`personas/Claudia.txt` 的 `share data:` 一条): 用户想打开 share data 时**总是回复 [Yes]**.
- **打开后**, 用户在 **设置 / 沟通 / 指令 / 重置 以外**的页面里:
  - 每切到一页, 把**那一页上用户和对方的数据**发给对方 (记成一条聊天里不显示的系统消息 `[系统·共享]`, **不调用 API**; 用户接着说话时对方就有这些数据); 两次发送至少隔 **30 秒** (冷却里切走的页, 冷却过了、还在那一页时才发).
    有数据的页: **计时器** (今天每一段 + 总计), **整点记录** (今天), **日历** (专注 / 休息 / 空闲 / 睡眠), **统计** (整点记录 / 联网理由 / 窗口 / 专注计时 / 合约记录). 联网 / 合约 / 成就页只显示悬浮窗, 不发数据. 黑雾中用户的数据写"黑雾中, 暂时无法提供".
  - 页面下方显示**聊天悬浮窗** (最近几条消息 + 输入框, 可折叠), 在里面发和收消息就是正常的沟通 (同样受"只有休息 / 空闲时能用"等限制).
  - 有数据的四页上, 悬浮窗标题右边有 **我的数据 / <人设名> 的数据** 切换 (对方有日程文件时才有; 人设名是不带后缀的人设名, 例如"Claudia 的数据", 英文"Claudia's data"; 视图标题和"这一页没有…的数据"也一样写人设名): 选"<人设名> 的数据"时, 一个只读的视图盖在原页面上 (计时器: 状态卡 + 今天的每一段; 整点记录: 今天已结束的格子; 日历: 月历, 可切四种时间; 统计: 各项排行), 内容和发给对方的是同一份 (24.11). 换页后回到"我的数据".
  - 在 设置 / 指令 / 重置 页里: 暂停 (不分享, 悬浮窗隐藏), 回到别的页继续.
- **回到沟通页 = 自动关闭**, 并**调用一次 API** 让对方总结这次 share data (按人设简短评价, 对用户说一句话; 只在这次真的看过数据页时才调用; 对方正在回别的话时等它空下来再发). 刚打开就还在沟通页不算结束.
- **邀请延迟生效**: `[share data]` 邀请绑定在对应消息的本机 `share_invite` 标记上, 等消息实际展示时才创建按钮及开始五分钟有效期; 打字延迟、对方专注延迟和用户不能沟通时的隐藏均不绕过。标记随本机聊天存盘以便重启恢复, 不同步 (share data 仍是本机界面状态), 展示后消费一次, 清空聊天会一起丢弃。只有标签、没有正文的邀请用一条邀请消息承载同样的延迟; 拒绝回复、被丢弃或查询中的回复不创建邀请。
- **前置 prompt XV**: "可发[share data]看双方OIT数据". prompt 还要求: 发 `[share data]` 时**必须在后面接上对用户说的话** (按人设, 说明理由或邀请), 不要只发标签; 这条消息照常显示 (只去掉 `[share data]` 本身, 不隐藏). 对方回复里写 `[share data]` (不分大小写) = **邀请**: 聊天页上出现"对方想看你们的数据 [接受] [拒绝]", 从邀请消息实际展示起 5 分钟内有效; 点**接受**才打开 share data 并跳到计时器页 (系统消息告诉对方"用户接受了"); 点拒绝则告诉对方"用户拒绝了". 对方不能自己打开.
- Claudia 的设定: 用户在 23:00-23:30 发起对话, 谈话结束后对方会发 `[share data]`; 在"特殊空闲"(24.11) 时主动发起对话则直接发起.
- **日程文件的新设定** (24.11): `重要活动发起谈话概率` (吃饭这类有名字的活动开始前, 没写的按空闲) 和 `特殊空闲发起谈话概率` (名字叫"特殊空闲"的那一段开始前; 没写的按空闲). 特殊空闲不再发"段开始后"的那一条 (24.4 I)，90+ 时改为段内必谈一次（24.20）; 主动发起的系统消息里会写明这一段的名字.

### 24.9 联合行动 (1.0.308)

用户邀请对方一起完成一次合约 (**"联合行动"**): 用户选词条和开始时间, 以"附件"的形式发给对方; 对方按人设日程决定接不接受; 合约期间双方的专注 / 休息同步, 结束后对方重新计算日程。

**1. 发起**
- 点聊天框上方的 **🤝**: 界面**移到合约页**, 让用户选词条; 开始行动的位置换成**"确定选择"** (合约页下方那条上写着"联合行动: 选好词条后点下面的「确定选择」(去别的页面 = 取消)"; 手机在右下角), 按它**不会开始合约**, 只是确定选择。已经有合约进行中 / 黑雾中 / 没选人设 / 还有联合行动没结束时不能发起 (弹提示)。去别的页面 (不点确定) = 取消。
- 确定选择后回到沟通页, 弹窗输入**开始时间** (时:分; 已经过了的算明天; 必须晚于现在、24 小时以内); 窗口下面实时算出**结束时间 = 开始时间 + 这些词条的合约时长** (初始 3 小时, 个别词条更长), 确定后 `🤝 联合行动 14:00 - 17:36 · N 个词条` 这一行**放在聊天框上方**, 点 ✕ 取消; 它**随下一条消息一起发** (不用写字也能发), 和 📎 附件一样: 对方不方便回复时消息留着, 隔 10 分钟再交给对方 (24.3), 对方不在 / 一直没回就一直等到约定的开始时间, 过了就算错过。
- 聊天里只显示 `🤝 联合行动 14:00 - 17:36 · N 个词条` + 用户写的字; 发给对方的是**原来"附件"的形式**: 前面是**合约的基础规则** (初始时长 / 目标生命值 / 危机等级与休息时间 / 空闲和离线 15 分钟 / 合约期间只能专注或休息), 然后是开始 / 结束时间, 危机等级和完成后的休息, 每个词条的名字 / 类别 / 等级 / 描述, 最后要求按前置 prompt 第 X 条回复 `[Yes]` / `[No]` (`comm_data.joint_text` / `CommData.jointText`)。

**2. 对方的回复**
- 回复里有 `[Yes]` = 接受, `[No]` = 拒绝 (两个都有按拒绝; 不分大小写和空格); `[]` 本来就不显示, 所以只回了 `[Yes]` / `[No]` 时聊天里写一行 `✓ 接受了联合行动` / `✗ 拒绝了联合行动` (不然这条邀请像没人回, 重开程序还会再问一次); 有别的话照常显示。回了 `[refuse to reply]` (不方便) 不算表态, 邀请留着重试, 但**最多留 5 分钟** (1.0.429: 用户发起的邀请超时也自动清理).
- 约定的开始时间已经过了才回 `[Yes]` = 错过; 一直没回复到了约定的开始时间也算错过。发出后 5 分钟没有 `[Yes]` / `[No]` = 邀请自动清理 (1.0.429, `JOINT_INVITE_TTL`). 接受 / 拒绝 / 错过 / 清理之后才能再发起新的联合行动.

**3. 开始合约**
- 对方接受后, **约定的开始时间一到**, OIT 提示 "约定的开始时间到了", 把约定的词条放进合约页 (没有合约进行中时), 用户照常按"开始行动" (所有原来的确认 / 限制照旧: 休息中不能开始、睡觉时间确认、录像确认……)。**用同样的词条**、时间在约定开始前 10 分钟 ~ 后 5 分钟之内开始的合约才算这次联合行动; 超过 **5 分钟**没开始 = **视为用户放弃** (状态仍记为"已错过"; 系统消息告诉对方"用户答应了联合行动, 却在约定的开始时间 (HH:MM) 过了 5 分钟后还没有开始合约: 视为用户放弃了 (放了你的鸽子)"; 1.0.337 起 5 分钟, 之前是 30 分钟)。
- 别的设备开始 / 结束的合约也算 (同步); 同一次联合行动只在主端记一次。

**4. 合约期间: 状态同步**
- 合约进行中, 聊天页上方对方的状态**跟着用户的计时器走**: 用户专注 → 对方"专注中", 用户休息 → 对方"休息中", 睡眠 → 睡眠中, 别的 → 空闲; 后面加 `· 联合行动`。不看人设日程; 对方这期间**不主动发消息** (24.4 的几种时机都不触发), 也不追问。
- 发给对方的 system 末尾会附一段 `[联合行动进行中] …用户现在休息, 你也休息…` (实时跟着变), 对方按它回复, 不再按原日程判断此刻能不能回复。
- **生命值损失 / 开始休息 (1.0.337)**: 合约进行中用户每损失一次目标生命值 (违反词条, 或点击解除网络禁令), 联合行动里记下 `[时刻, 内容]` (`joint.hp`, 随设备同步; 内容就是违规记录页里的那段提示, 最多记 30 条), **当时不告诉对方**; 到**下一次用户开始休息**或**合约结束**的时间点, 才把这些记录 (`HH:MM:SS 内容`) 写进一条系统消息 `[系统·联合行动] …` 发给对方, 然后清空。**开始休息时**这条消息还会写明**这次休息的时间** (`联合行动中用户 15:20 开始休息了: 这次休息 25 分钟, 到 15:45 结束…`, 没有生命值损失也照样告诉), 并且**调用一次 API** (请求种类 `joint_reply`), 让对方可以回应一句 (回复和普通回复一样显示; 不方便就返回 `[refuse to reply]`, 信息已经在聊天记录里, 不会丢)。合约结束时只有**有生命值损失的记录**才再调用一次 API (没有记录就和以前一样只记一条系统消息)。对方正在回别的话时, 这次调用最多等 3 分钟 (`_joint_pending`), 之后就算了; 对方不方便 / 不是主端 / 没有 API 也不调用。电脑靠 `app._joint_break_watch` 每秒看一次计时器是不是在休息 (开始 → `comm.joint_break_started`, 结束 → `comm.joint_break_ended`); 手机是 `Core.jointBreakWatch`。 **告诉对方的休息时间不含合约开始前积攒的休息时间 (1.0.339)**: 开始休息时这次休息的总长里, 合约前积攒的那部分 (`_break_pre`, 放在最后用) 先减掉, 对方只收到合约里得到的休息时间。

**5. 合约结束: 休息同步 → 重新计算日程**
- **完成时的效价奖励**：人设模板可用 `[valence:events]` 中的 `joint_completed:X` 声明共同顺利完成联合行动时的基础效价奖励，X 为 0–100 的整数；未声明或格式错误时为 0。Claudia 为 30，由真实合约的 `completed` 结算直接入账，无需模型判断或额外请求。失败、放弃、错过、仅开始和单人合约不触发；重复结束回调、重启与同步不重复发奖。奖励入账到联合行动所属对象，期间切换聊天不影响归属。此奖励不参与聊天条件的冷却、连锁或爆发倍率，沿用未原谅冒犯的正向效价倍率及 -100 至 100 上下限。`intellectual_resonance` 只表达深入理解与自律带来的共鸣，不包含完成合约的奖励含义；模型不得因同一次完成事件再套用其他效价条件。
- 合约结束 (完成 / 失败 / 空闲 / 离线 / 提前终止) 时: 对方**同步得到同样的休息时间** (合约给的休息, 完成给全额, 没完成按比例, 可能是 0), 从合约结束那一刻起休息, 状态显示"休息中 · 联合行动"; 并记一条系统消息 `[系统·联合行动] 联合行动顺利完成了 …` / `联合行动失败了: 用户在合约中违反太多次 …` (1.0.337 起如果合约期间有生命值损失还会带上 `合约期间用户损失生命值的记录 (时间 内容): …`, 并调用一次 API 让对方回应; 聊天里不显示, 发给对方的历史里有, 所以 Claudia 才知道该不满 / 该聊"合约"主题; 不是 `[系统]` 开头, 所以不算主动消息, 不影响 10 分钟间隔和提示音)。
- **用户结束休息 → 对方也结束 (1.0.337 修复)**: 合约结束后对方的休息本来固定到 `rest_until`, 用户在这期间把休息走完或提前结束 (暂停休息) 时对方却还在休息。现在用户的休息一结束 (`joint_break_ended`), `rest_until` 立即改成现在, 对方的状态变成空闲 / 专注, 休息结束的时刻 T 也成了现在 (下面的重新计算从这一刻起算), 并记一条系统消息 `用户 HH:MM 结束了休息 (原定休息到 …), 你也跟着结束休息, 现在需要重新计算日程`。合约结束时被合约停掉的休息 (失败 / 提前终止) 不算 "用户结束了休息", 对方仍休息到合约给的时间。合约进行中对方的状态一直是实时跟着计时器的 (用户休息结束 → 对方马上不再"休息中")。 **1.0.338**: 合约进行中用户结束休息 (走完 / 提前结束) 时也记一条系统消息 `联合行动中用户 HH:MM 结束了休息, 现在用户空闲, 你的状态也跟着变成空闲 (不再休息)`, 这样对方的聊天记录里不会还停在开始休息时写的"你与用户同步休息"上 (状态栏和 system 末尾本来就是实时的)。
- **休息结束的时刻 T 落在循环里** (人设的 `[循环 …]` 的范围): 对方**立即开始专注**, 从 T 起重新按 **N 分钟专注 + F(N) 分钟休息**交替, 到那个循环结束为止 (循环结束后又是原来的日程; 第二天的同一段循环不受影响)。状态、主动发消息的时刻、发给对方的日程都按重新计算后的 (system 末尾附 `[联合行动之后重新计算的日程] …` 列出重新计算后的循环)。
- **T 落在循环以外** (和原来的"空闲" / 睡眠 / 吃饭重叠): **不影响**, 照原日程。
- **合约结束后对方继续跟着用户 (1.0.404 修复)**: 以前对方的休息固定从合约结束起按合约给的那几分钟算, 不看用户什么时候真的休息 —— 合约结束时用户往往还在专注 (之后的休息要等这轮专注结束, 长度是建议休息 + 积攒的休息时间), 对方却已经在"休息中"了。现在这个同步阶段 (`state = rest`, `rest_until` 是预计结束的时刻) 里:
  - 对方的状态**继续跟着用户的计时器**: 用户专注 → 专注中, 用户休息 → 休息中, 睡眠 → 睡眠中, 空闲 → 休息中 (后面都加 `· 联合行动`); 发给对方的 system 末尾也相应写明 (用户还在专注 / 睡眠时写 "合约虽然结束了, 你与用户仍然同步: 用户现在专注, 你也专注; 用户休息时你才休息, …").
  - **用户还在专注 / 睡眠**: 主端每秒看一次, `rest_until` 不到 90 秒就往后顺延 3 分钟 (`JOINT_FOLLOW_STEP`), 一直到用户的休息结束 (`joint_break_ended`) 为止; 最长到合约结束后 3 小时 (`JOINT_FOLLOW_CAP`)。用户**空闲**不顺延, 到 `rest_until` 就结束 (用户专注结束后等着开始休息的那两三分钟还算在里面)。
  - **用户正在休息** (合约结束时正好在休息, 或之后开始休息): `rest_until` 改成用户这次休息**真正的结束时刻** (含合约奖励和积攒的休息时间, 随用户暂停休息 / 走完而变), 不再按合约给的那几分钟算; 合约结束时用户正在休息 → 一开始就休息到这次休息结束 (`comm.break_end_fn` / `Comm.breakEndFn`)。
  - 用户的休息一结束, 同步阶段立即结束 (见上), 重新计算日程。
- **联合行动里合约前保存的休息时间收起来 (1.0.404)**: 联合行动的合约开始时, 开始前积攒的休息时间 (`break_carry`) **收起来** (合约 `live.stash`, 合约开始后 `break_carry` 显示 0): 合约中看不到、不能用 (`pre = 0`, 休息只有合约中得到的部分), **不会触发"支援短缺"** (没有可用的部分, 也不会用超); 合约页右上角的 "暂停休息: 合约前积攒的时间不打折" 这一行也不显示。合约结束 (完成 / 失败 / 提前终止) 时**原样还回去** (记录里 `stash`; 积攒的休息时间 = 还回的 + 奖励)。判定在合约开始前: 约好的词条 + 时间在约定开始的前 10 分钟 ~ 后 5 分钟 (`comm.joint_pending`); 之后没能算作联合行动 (差了一瞬间) 就马上还回去。
- **联合行动期间对方的统计 → 日志 (1.0.404 检查)**: 对方的时间线 (`routine` 的 `tl`, 整点记录格子从它算) 每 30 秒补一次, 联合行动的状态变化 (开始 / 结束 / 休息结束) 前先补一次; 联合行动开始**之后**的时间按用户的专注 / 休息 / 睡眠记 (标签 `联合行动`), 开始之前没记到的部分按原日程记 (以前整段没记到的时间都会被记成联合行动); 联合行动里用户空闲的时间记成"空闲" (以前整点记录会写出 "联合行动" 三个字)。休息结束后的循环重新计算 (`shift_for_joint`) 本来就进了时间线。

**6. 其他**
- 联合行动属于发起它的那个聊天对象 (换人设就看不到, 也不影响别人); 清空聊天 = 联合行动作废 (包括进行中的同步状态)。
- 自检: `python -m comm` (联合行动整条链路: 选词条 / 开始时间 / 打包 / [Yes] [No] / 开始 / 同步状态 / 结束 / 重新计算日程 / 设备同步), `python comm/comm_data.py`; 手机 `CommTest.jointAction`。

### 24.9.3 对方主动发起联合行动 (前置 prompt XII, 1.0.317 起)

### 24.4.2 主动发起的对话不能 [refuse to reply] (1.0.333)

- 规则 I - IV 触发的主动消息 (kind `proactive`, 包括非正在聊天的对象) 的系统触发语不再写"不方便就返回 [refuse to reply]", 而是"这条必须发出, 不要返回 [refuse to reply]". 对方还是回了 (而且不是 `[refuse to reply][模块]` 这种查资料) → OIT 再调用一次 (`PRO_NO_REFUSE`: 这是你主动发起的对话, 不能拒绝, 请主动发一条), 第二次的回复照常显示; 第二次还拒绝才算不发. 回复用户 / 追问等别的请求不变.

### 24.9.4 对方切断谈话 (前置 prompt XIII, 1.0.318 起)

- 对方被骚扰时在回复里写 `[cut off][N]` (N = 屏蔽分钟数; 没写 = 10 分钟, 最多 24 小时, 最少 1 分钟; 任何一次回复都可以, 包括它的话说到一半的那条): OIT 记下"切断到什么时候" (再次切断取更晚的), 这条回复里别的话照常显示, 并给对方记一条系统消息 `[系统·切断]` (它的历史里有).
- 切断期间: 用户**发不了消息** (聊天页上方写"对方切断了与你的谈话, 还有 N 分钟 (到 HH:MM)"), 对方也不会主动发 / 重试 / 追问 / 回应联合行动, 不在这个聊天里的对象也不会来找你. 到点自动恢复. **清空聊天不能解除切断**; **开发者模式不受限制**. 切断是跟着聊天对象走的 (每个人设各自), 随设备同步 (取更晚的).

### 24.10 限时网络 (前置 prompt XIV, 1.0.348 起)

- 对方 (AI) 默认不能联网. 它在回复开头写 `[apply for network][N]` (N = 分钟数; 没写 = 5, 最少 1, 最多 30) 申请限时网络, 后面接着对用户回复当前话题 (比如说自己在等冷却期; 这条话照常显示, 方括号不显示). 回复用户 / 重试 / 追问 / 主动发起这几种请求里写才有效.
- 等 **2 分钟** 之后 OIT 再调用一次接口 (kind `net`, 系统消息 `[系统·网络]`: 网络已开通 N 分钟, 到 HH:MM), 这一次请求**带联网搜索**, 对方搜索并回复用户 (这条必须发出, 回了 `[refuse to reply]` 会再要求一次). 之后网络开着的 N 分钟里, 用户再说话 (以及追问等) 发给模型的请求也都带联网搜索.
- 网络关闭后有 **10 分钟冷却期**; 申请中 / 冷却期里再写 `[apply for network]` 无效 (这条话照常显示). **网络开着的时候再申请**: 不用再等, **也不重新开通、不延长**现在的开通时间, 但会**马上再调用一次**接口让它搜 (`kind` `net_again`, 系统消息说明网络还开着、只到 HH:MM), 不会等到 2 分钟之后. 搜索那次请求失败 → 60 秒后再试, 最多再试 2 次, 还不行就放弃 (进入冷却). 清空聊天 / 换聊天对象 → 等着的申请作废.
- 状态 (`cfg["net"]` / `NetState`: ts, pid, n, due, until, cool, st = wait / on / cool, tries, again) 随设备同步 (文档键 `net`, 后改的为准); 只有最后有人操作的设备 (leader) 去开通和调用.
- 四家的联网方式 (`ai_assist.web_mode` / `Ai.webMode`):
  - **Gemini** (原生 gemini 协议): 请求里带服务端工具 `tools: [{"google_search": {}}]`, 搜索由 Google 完成, 回复仍取 `candidates[0].content.parts`.
  - **Claude** (anthropic 协议): 请求里带服务端工具 `web_search_20250305` (最多搜 3 次), 搜索由 Anthropic 完成; 回复内容里夹着 `server_tool_use` / `web_search_tool_result`, OIT 只取最后一次搜索结果之后的文字; 服务端回 `pause_turn` (搜得太久) 时原样带回去接着跑 (最多 3 次).
  - **ChatGPT** (`api.openai.com`): 改走 Responses API (`POST /v1/responses`), 带 `web_search` 工具, 系统提示放 `instructions`, 回复取 `output` 里 `message` 的 `output_text`.
  - **DeepSeek 和别的 OpenAI 兼容接口** (中转 / 本地模型; 官方没有搜索接口): 函数调用. 请求带 `tools: [web_search(query)]`, 模型要搜时由 **OIT 自己搜** (`GET www.bing.com/search?q=…&setlang=zh-hans` (不能用 cn.bing.com/search: 它会 302 到首页, 1.0.349 因此什么都搜不到), 不要 Key, 取前 5 条的标题 / 链接 / 摘要), 把结果作为 `tool` 消息交回去; 最多搜 3 轮, 之后 `tool_choice: none` 要它直接答.
  - 服务商的接口不认搜索 (400 / 404 / 405 / 422): 不联网再答一次, 系统提示里说明"这次没能联网, 凭已有知识回复". 网络 / 鉴权 / 5xx 等其他错误照常报错 (搜索那次请求会按上面的规则重试).
- 过滤: 由 OIT 自己搜索的方式 (DeepSeek 等) 在网络开着期间, 搜索页的域名 (`cn.bing.com`, `www.bing.com`) 和 AI 接口的域名一样不被过滤代理 / VPN 拦 (PC `app._api_hosts`, 手机 `Core.apiHosts`); 搜索请求不带任何 Key.
- 日志: comm.log 里有 `NET 申请 / 开通 / 带联网搜索 / 搜索请求失败` 行.

### 24.13 人设里的判定由 OIT 算: [condition] (前置 prompt XVI, 1.0.392 起)

- 人设可以让对方在某些情况下"先判定条件再回复" (默认 Claudia: 用户提出发展亲密关系时): 对方在回复里**只输入 `[condition]`** (不显示给用户, 和 `[calendar]` 这类查询一样被藏起来), OIT 马上算出每个条件的**当前进度**和**满没满足**, 作为系统消息 (用户看不到) 发回去, 再调用一次让对方回复用户 (算入 `MAX_INFO_ROUNDS`). 条件由 OIT 判定, 对方不要自己推算, 也不要编造数字.
- 条件建议统一放在 `X_templates.txt` 的 `[condition]` 区块中，继续兼容人设正文及其他配套文件，字段使用 routine 风格的 `字段:数值/列表`；默认 Claudia 定义以下五项，但其他人设可以删减项目、改门槛：
  - I. 包括今天在内的前 30 天, 和对方共同完成的联合行动 (真实合约记录, 24.11) 里难度 (危机等级) ≥ 15 的有 ≥ 24 场. 只有带日程文件的人设记得到 (`routine.KEEP_JOINT` 因此从 20 提到 120).
  - II. 用户在包括今天在内的前 60 天专注 ≥ 420 h 并且空闲 ≤ 210 h. 用户的计时记录只留 7 天, 所以沟通模块自己每小时 (和每次判定时) 把最近 7 天的 (专注秒, 空闲秒) 存进 `comm_config.json` 的 `cond_days` (最多留 70 天); **没记录到的天不算进去, 回复里会写"OIT 只记录了其中 N / 60 天"**, 所以新版本刚装上时这一条一定不满足.
  - III. 双方一共 ≥ **500** 条信息 (1.0.394 从 200 改成 500; 不算还藏着的). 1.0.397 起数的是**总数**: 聊天记录本地最多留 600 条, 超过的从最老的删, 删掉的条数记在聊天状态的 `msg_gone` 里 (`Comm.msg_total` / `msgTotal`), 所以要 1000 条也数得出来; 清空聊天归零.
  - IV. 用户今天的专注 ≥ 8 h.
  - V. 现在是日程里的"特殊空闲"时段 (24.11).
- 返回给对方的文字: 每个条件一行"编号.说明: 当前 …, 要求 …, 已满足/未满足", 最后一行结论 (全部满足 / 没有全部满足).

### 24.16 起点平移 / [messages] (前置 prompt XVIII, XIX, 1.0.402 起)

- **是什么**: 沟通页 🕰 按钮（⏳ = 等对方回复，再点 = 取消）：用户请求平移对方日程的**初始起点**。允许的新时刻来自人设配套模板的 `[shift]` 区块 `range:[最早时刻,最晚时刻]`，端点均包含，时刻限 0:00–23:59，最早大于最晚表示跨午夜。未声明区块时允许全天；区块缺失端标、重复、空白、未知字段或非法钟点时拒绝新请求。默认 Claudia 在 `Claudia_templates.txt` 声明 4:00–9:00。平移量仍须是 `COMM_SHIFT_STEP_MINUTES`（15 分钟）的整数倍，相对明天当前起点校验；保留旧存档中的自定义起点，不擅自取整。只对有日程文件的人设有效，不修改人设 / 日程文件，记录存在聊天状态里。发出请求和最终同意落盘前均重读当前范围，文件修改后不再合法的请求不生效。
- **流程** (和 share data 的"先问对方" 24.12 一样): 点 🕰 → 输入新起点 → `shift_request` 检查 (范围 / 15 分钟步长 / 和明天的起点相同 / 对方在专注或睡眠时问不了 / 上一个请求还在等) → 本机是主端时每秒的 `_shift_tick` 发 `shift_ask` 请求, 系统消息以 `[系统·平移]` 开头, 写明从几点平移到几点、明天起生效、范围, 要求回复 `[Yes]` / `[No]`. 回 `[Yes]` → 记录; `[No]` / 没表态 / `[refuse to reply]` / 出错 / 5 分钟没回 (`SHIFT_ASK_TTL`) → 不变, 弹提示. 只回 `[Yes]` / `[No]` 时聊天里写一行 `✓ 同意了起点平移` / `✗ 拒绝了起点平移`.
- **生效时间**: 同意时记 `{ts, d: 明天的日期, s: 新起点分钟, f: 平移前的起点}`; `Routine.start_for(d)` / `startFor`: d 这一天的起点 = 生效日期 <= d 的最近一条 (同一天有好几条取最后记的), 没有就是日程文件里写的. `wake_at` 用它, 所以明天起床时刻 (= 今天睡眠段的结束)、整天的日程、共时闹钟的起床时间都跟着变, 今天已经排好的不变. 过去的整点记录 / 数据不受影响.
- **记录跟着聊天对象走** (`shift`, 存在各自的聊天文件里, 随设备同步: 文档键 `shift:<pid>`, 两边的记录按 `ts` 合并去重, 最多留 `SHIFT_KEEP` = 30 条). 所以**手机和电脑的日程一致**. 清空聊天记录不清平移 (平移是日程的事, 不是记忆).
- **告诉对方**: 平移过的话, 每次请求 system 里长期记忆最前面有一行 `- 【系统记录】日程起点已被平移 (人设和日程文件里写的'初始起点'不再适用, 以这里为准): 自 日期 起初始起点是 H:MM …` (和 24.15 的亲密关系记录同理), 不然它会按人设里的旧起点理解自己的日程.
- **查询聊天记录数**: 对方回复里写 `[messages]` (前置 prompt XVIII) → OIT 把双方互相发过的信息总数 (`msg_total`, 和 `[condition]` III 同一个数, 本地被 `KEEP` 砍掉的也算) 告诉它, 再调用一次让它回复用户 (和 `[condition]` 一样走查询轮, 这条查询不显示). 默认人设 Claudia 的同意条件: 聊天记录至少 200 条才回 `[Yes]`, 否则 `[No]` (写在 `Claudia.txt` 的"起点平移"段, 不是写死在代码里).
- 我替用户定的假设: 新起点是绝对时刻 (不是 +N 分钟); 一次请求 = 一个新起点; 「明天」按请求被同意那一刻的日期算; 同一天再平移以后一次为准; 其它人设没有同意条件时由它按人设自己判断.
- 自检: `python -m comm` (起点平移一段), `CommTest.startShift` + `RoutineTest`.

### 24.17 日程跟随 (设置 → 沟通 → 📅 日程跟随, 1.0.406 起)

- **是什么**: 开关 (默认关, 随设备同步: 文档键 `sfollow`, 本地键 `sched_follow`). 开着时, 对方的状态 (按人设日程算出来的, 就是聊天页顶上那一行: **专注 / 休息 / 睡眠 / 空闲** 四种, 别的名字一律算空闲) **每变一次**, 系统弹一个提示窗 (电脑 `toast.notice`, 手机 `Core.notice`): "{name} 开始专注了, 要跟着专注吗?" / "开始休息了" / "去睡觉了" / "现在空闲了", 按钮 **不用** / **跟随**. 提示里指代对方一律用 `{name}` (人设名, 没选人设时 "AI"), 不写"对方".
- **跟随 = 按对应的按钮**: 专注 → 主按钮 (空闲 → 开始专注; 休息中 → 暂停休息并开始专注); 休息 → 专注中按主按钮 (结束专注, 进入休息), 空闲时按副按钮 (用积攒的休息时间, 没有积攒的会提示); 睡眠 → 先结束专注 / 休息再 `start_sleep`; 空闲 → 结束专注 / 休息; 睡眠中而对方变成别的状态 → 先起床. 合约中 / 外出中不能跟随 (弹提示).
- **什么时候不问**: 用户的计时器已经是同一种状态 (专注↔focus, 休息↔break, 睡眠↔sleep, 空闲↔idle); 用户在外出 (out); 本机不是焦点设备 (最后有人操作的设备, 与调用 AI 的聊天主端独立); 没选人设; 换了聊天对象 (重新记状态, 不当成变化). 焦点转走时撤掉本机尚未回答的日程跟随提示.
- **合约期间自动关闭, 结束再开启**: `sf_live()` = 开关开着 **并且** 用户没有合约 (`contract.active`) **并且** 没有联合行动的同步阶段 (`joint_live()`: 合约进行中 + 合约结束后对方跟着用户休息的那段). 不 live 时不看对方的状态, 并且**忘掉上一次的状态**; 重新 live 时先记下对方此刻的状态、不提示 (合约里对方被改成的状态、合约结束的那一刻换回日程的状态都不算"变化"), 之后的变化照常问. 还没回答的提示窗在合约开始 / 开关关闭时自动撤掉; 又变一次时换成新的提示 (旧的撤掉). 开关本身不被改动 (所以合约结束后自动是"开启"的).
- 日志: `comm.log` 里 `FOLLOW 对方 X → Y: 问用户跟不跟随`.
- 我替用户定的假设: "状态改变" = 四种显示状态的变化 (专注里换了名字不算); "跟随" = 让用户的计时器进入同一种状态 (不是自动开始, 要点"跟随"); 对方变成"休息"而用户空闲且没有积攒的休息时间时只提示"还没有积攒的休息时间"; 手机和电脑各自按本机的计时器判断.
- 自检: `python -m comm` (日程跟随一段), `CommTest.scheduleFollowAndLateRelease`.

### 24.20 情景模拟与情绪张力

- **张力的通用含义**：对所有角色，`TENSION` 都表示行为、动作与语言的激烈/直接程度；数值和生效档位据此调节表达强度。人设决定各档位的情绪、表达方式，以及 `BURST` 期间和 `SHAME_AFTERMATH` 冷静期的具体反应，但不能改写张力的通用含义。不得把张力本身解释为好感、爱情或关系进度，也不得补设人设未定义的情感与性格含义。Claudia 可将修正冲动、占有主导欲与深层庇护欲作为自身张力升高时的情绪动因；仓库与双端内置文本同步。结算、同步和阶段切换机制沿用原规则。

### 24.21 冒犯记录与原谅

所有人设（包括 Assistant 和自定义人设）在各自聊天状态 `interaction.offenses` 中独立保存冒犯记录，与自动摘要 `mem_auto`、实时事件 `mem_live` 分离。模型根据人设边界和实际对话判断；普通分歧、拒绝和用户的脆弱不自动等于冒犯。每条记录含用户消息 UID `id`、原消息发送时刻 `at`（毫秒）、至多 120 字的简短原因 `reason`、修改时刻 `ts` 和 `forgiven`。同一消息归为一条，不重复记账；旧存档缺字段视作空账本，不凭历史猜测补记。

通过原生 `oit_reply.offenses` 数组提交：每项 `index` 对应本轮待判断的真实用户消息；`action=add` 时 `target` 为空、`reason` 简述冒犯，时间由程序取该消息的真实发送时刻；`action=forgive` 时 `target` 必须匹配当前系统账本里的记录 ID，`reason` 简述确实决定原谅的依据。没有任意删除或自动过期操作。道歉、要求删除、时间流逝、情绪好转都不直接表示获得原谅；须由角色确实决定原谅后逐条清除。已原谅的原因擦除，保留 ID、时间及原谅墓碑用于去重与同步。Claudia 的人设规定每天最多原谅一条，以系统本地日期为准；这是角色提示词约束，不改变其他人设的原谅策略。

只有最终正常成功的 `user` / `retry` 回复结算；按待判断消息顺序，先应用该消息的新增或原谅，再计算该消息的效价变化。非本轮序号、正文伪造控制文字、拒绝、错误、空回复、未完成查询、过期或取消的回复不生效，已结算消息不重复处理。控制数组不进入聊天正文、语音与历史；有效账本作为系统记录随每次请求提供，状态另带 `OFFENSE_COUNT`、`VALENCE_RISE_RATE`。

每条未获原谅的冒犯使 Valence 平衡点降低 10，最低为 -100。双端根据 `valence_initial` 中保存的人设基础值与现有账本实时计算平衡点，原谅后按剩余条数重算。已初始化的当前效价按原有自然回归节奏趋向新的平衡点。

每条未获原谅的冒犯也使 Valence 正向增长额外倍率减少 0.2：`max(0, 1 - 0.2 × 未原谅条数)`；例如 0 / 1 / 2 / 5 条分别为 1 / 0.8 / 0.6 / 0。默认值在桌面 `config.COMM_OFFENSE_VALENCE_RATE_PENALTY` 与安卓 `Cfg` 中保持一致。沿原有单条件冷却 → 连锁 → 爆发倍率后，再对正数变化乘冒犯倍率并向零取整，最后沿用单消息 ±40 与总值 ±100 限制；负向变化不打折。自定义爆发结束产生的正向变化也应用该倍率。原谅一条后按剩余条数即时恢复倍率，不追补先前受抑制的增长。

账本随对象落盘，重启、跨午夜、普通清空聊天、自动摘要压缩均不删除，清空聊天仍重置其他既有聊天状态。设备同步逐条合并账本，原谅墓碑不可被旧的未原谅版本覆盖，情绪整体版本落后或聊天清空世代不同也不丢失冒犯。完整数据重置仍删除整份应用数据。Claudia 未原谅记录非空时禁止演奏和接受 / 发出告白，拒绝时由人设提示词从未原谅原因中随机选择一条含蓄暗示，不逐字引用或编造；准备、延迟播放与正式关系确认时再次检查；新增冒犯后停止正在播放的演奏并取消待播曲目，高效价、张力、爆发或已有亲密关系不绕过，也不自动解除已有关系。其他人设仅沿用通用记录与效价倍率，具体互动由自身人设决定。

检查覆盖：`python checks/_comm_tools_check.py`、`python -m comm`，安卓 `CommOffensesTest`、`CommTest.offensesAndRelationshipGates` 与原生工具协议测试。


Claudia 在睡眠时发送的用户消息记入 `pending_sleep`，即使消息等到起床后才统一判断，仍按发送时段结算效价：正向变化乘 0.5，负向变化乘 0.2；张力和其他人设不受此倍率影响。该标记随聊天状态同步，消息结算后删除。系数在桌面 `config.COMM_CLAUDIA_SLEEP_VALENCE_RISE_RATE` / `COMM_CLAUDIA_SLEEP_VALENCE_FALL_RATE` 与安卓 `Cfg` 中保持一致。

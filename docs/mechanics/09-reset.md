# 9. 重置 (Reset 页)

[← 返回目录](../../MECHANICS.md)

- 需要输入 `RESET`, 再确认一次.
- 重置时:
  - 先解除网络限制: 重新启用网卡, 关闭过滤代理, 还原系统代理;
  - **先请每台绑定的设备 (第 15 节) 也清空 OIT 的数据**, 但**不解除绑定**; 它们再转告各自绑定的其他设备 (同一个请求只处理一次).
    收到请求的设备照本节重置 (同样保留绑定), 重新打开后提示"某某重置了 OIT, 本机的数据也一起清空了".
    对方连不上 (最多等 3 秒), 或者是不认识这个请求的旧版本时, 记下来, 下次连上时先把请求送过去; 送到之前不和它合并数据 (显示"同步失败: wipe-pending"), 免得它的旧数据又回来;
  - 删除整个数据目录 (以及旧版本 `mrsTimer` 的目录): 学习记录, 整点记录, 统计, 联网额度与日志, 名单, 设置, AI 配置全部删除;
    只留下设备同步的绑定 (本机的设备 id, 绑定的设备和密钥, 没送到的清空请求, 解除绑定的计划);
  - 进行中的专注不会被记录;
  - 不留任何记录 (旧版本留在数据目录外的卸载次数文件 `Obliphur's Integrated Terminal.uninstall.json` 也一并删除);
  - 程序随即自动重新打开, 就像第一次安装: 所有设置都是默认值, 名单为空, 弹出介绍窗口, 重新开始 72 小时配置期.
    网络按默认设置 (Proxy + 黑名单 + 空名单) 重新接管, 实际上什么都不拦.
- 程序文件不会被删除. 不想再用时, 使用卸载程序 (9.1). 不要只是重置后关闭程序: 关闭程序本身会断网 (2.7).
- Reset 页不再有"解除所有绑定"; 解除绑定在 设置 → 基本设置 → 设备同步 里一台一台地解除 (15.1). 等待中的解除绑定重置后照样留着.

就这样回到一切之初,修正错误的抉择.

### 9.1 卸载 (uninstall.py)

- 双击项目文件夹里的 `uninstall.bat` (或 `python uninstall.py`). 独立运行, 主程序打不开也能用. 启动时申请管理员权限.
- 窗口上方先显示检测到的状态: 正在运行的 OIT, 系统代理, 被禁用的物理网卡, 数据目录大小.
- 需要输入 `UNINSTALL` 确认. 之后按顺序执行:
  1. 结束正在运行的 OIT (连同它正在执行的断网命令). 认法: 命令行里带着本文件夹的 `main.py`, 或者监听着过滤代理端口 (17890 ~ 17910) 的 python 进程.
     必须先结束它, 否则它会马上把网断回去;
  2. 还原系统代理: 有 `sysproxy_backup.json` 就按它还原; 备份丢了 (或备份里的"原设置"本身就是 OIT 的端口) 而代理仍指向 OIT, 就直接关掉代理;
  3. 重新启用全部被禁用的物理网卡 (和程序解除限制时一样, 不区分是不是本程序禁用的);
  4. 删除数据: 和重置删除的范围相同 (数据目录, 旧版本 `mrsTimer` 目录, 旧版本的卸载次数文件), 以及设备同步加的两条防火墙规则 (15.3) 和开机自启动的计划任务 (3.4), 绑定也不留.
     删除前先请每台绑定的设备清空 OIT 的数据, 并**解除和本机的绑定** (它们之间的绑定不动, 照样转告其他设备清空);
     对方是旧版本时只让它解除绑定并删掉本机的数据; 连不上的跳过 (卸载之后没法再送). 不会重新打开程序;
  5. 删除程序文件夹 (默认不勾): 关闭卸载窗口后由后台 PowerShell 删除. 只有文件夹里有 `main.py` / `app.py` / `net_guard.py` / `uninstall.py` 时才会删;
     文件夹是 git 仓库时会额外提示. 被资源管理器 / 终端 / 编辑器打开着时可能删不干净, 需要关掉它们后手动删除.
- 1 ~ 4 一定会做: 和重置一样, 立即恢复网络的代价是全部数据, 没有"只恢复网络, 保留数据"的选项. 某一步失败时会标红, 可以再运行一次.
- 卸载不记录任何东西, 也不需要等待冷静期.

### 9.2 手机上卸载 OIT: 卸载保护

Android 不会在应用被卸载时通知应用自己, 所以直接卸载 (系统设置 / 桌面长按) 其他设备来不及知道. 有两道防线:

**1. 设备管理员** (`OitAdmin`, 不要求任何设备管理策略, 只用"取消激活"这个动作):
- 绑定了其他设备时, 设置 → 设备同步 里有"卸载保护"一栏 (没启用时标橙色), 按"启用卸载保护"打开系统的激活界面.
  (1.0.234 修复: 以前带了 `FLAG_ACTIVITY_NEW_TASK`, 系统的 `DeviceAdminAdd` 看到它会直接关掉, 界面一闪就没了. 现在从界面的 Activity 里用 `startActivityForResult` 打开.)
- 取消激活 (`onDisabled`) 的那一刻 OIT 还在, 马上做和 Reset 页"卸载 OIT"一样的事: 请每台绑定的设备清空 OIT 的数据并解除和本机的绑定, 本机的数据也清空; 没有绑定的设备时什么都不做.
- **实测 (vivo V2168A, Android 11): 激活之后系统自带的卸载界面和 `adb shell pm uninstall` 照样直接把 OIT 删掉, 并不要求先取消激活**, 所以这一道在这类手机上**拦不住卸载**
  (系统的激活界面上还有一个"卸载"按钮). 它只在系统真的要求先取消激活的手机上有用. 取消激活时 OitAdmin 会往 `files/admin.log` 记一行 (排查用; 手机的 logcat 看不到).

**2. 其他设备发现对方没了** (不依赖手机配合, 1.0.235): 绑定的设备**连续 24 小时**对本机"拒绝连接" —— 同步端口 (17930~17939) 每次同步都是"拒绝连接" (不是超时: 主机在线, 只是没人听),
并且联动程序的端口 (17940) 此刻也"拒绝连接" (有人听就不算) —— 就当它的 OIT 和联动程序都没了 (卸载 / 强行停止): 本机**只解除和它的绑定, 并清掉本机保留的它的数据** (账, 状态: `unpair`),
弹出提示; **本机自己的数据不动** (1.0.237: 以前这里会清空本机, 绑了两台手机 (旧的那台已经卸载) 就会清掉电脑的数据, 不对). 每台能连到它的设备各自判断, 不需要谁转告谁.
- 记在每台设备的绑定记录里 (`refused_since` / `refused_last`): 两次"拒绝连接"之间隔了 30 分钟以上 (本机睡了 / 关了), 中间同步成功过, 或者出现别的错误 (超时, 断网), 都重新算 24 小时.
- **外出 / 关机 / 断网期间不算** (1.0.236): 本机看到的外出 (外出期间可以关掉 OIT, 联动程序也不启动它, 8.4 / 21), 对方关机 (最后的状态是收到关机指令 / 没电, 15.4) 或换成了 Adapter 断网 (15.5),
  本机在别的虚拟桌面 / Adapter 断网时: 不判断, 并且把"拒绝连接"的记录清掉, 回来之后重新算 24 小时.
- 手机被杀掉 (从最近任务划掉) 不会误判: 保活闹钟 45 秒内把 OIT 和联动程序叫起来; 手机关机 / 断网是超时, 不是拒绝连接. 手机上的 OIT 被"强行停止"并且超过 24 小时没人再打开也会被当作卸载 (同样是绕过).
- 手机上对电脑同理 (电脑关机 / 睡眠是超时; 电脑上 OIT 卸载了联动程序也没了才算).
- 没有启用 / 没有效果时还有第三道: 卸载了的那台一直显示"同步状态: 拒绝连接", 在 15.1 里解除绑定 (冷静期 120 小时).
- 备份: `allowBackup=false`, `dataExtractionRules` 把云备份和设备间迁移都排除, `fullBackupContent=false`, 数据不会被系统备份 / 换机迁移带走.

### 9.3 数据的连续性 (电脑): 搬走 / 倒回去的数据会被清掉

OIT 的数据在 `AppData\LocalLow\<程序名>`, 本来只有 OIT 自己写. 拿旧的备份覆盖回来可以躲开已经记下的违规 / 额度 / 冷静期, 整个文件夹复制到别的电脑上可以另起炉灶, 所以 (`continuity.py`):
- **连续性记录**: 数据里的 `continuity.json` = (世代 ep, 序号 seq, 封印 seal). 序号每 30 秒 +1 (和关闭时). 封印是 Windows **DPAPI** (绑定这台电脑和这个用户) 加密的 "世代|序号".
- **锚点**: 数据文件夹**以外**三个地方同样记着 (世代, 序号, pending), 同样用 DPAPI 封着: 注册表 `HKCU\Software\Obliphur\OIT`, `ProgramData\Obliphur\OIT\<用户名>.anchor`, `LocalAppData\Obliphur\OITnchor.dat`.
- **其他设备**: 同步的状态里带着 `cseq` / `cep`, 其他设备会转来"它们记着的本机上次的状态"; 同一世代里它们记着的序号比本机的大 20 以上 (10 分钟) = 本机被倒回去了
  (整盘镜像还原这类连锚点一起倒回去的靠这个). 发现时在锚点里标记 pending 并马上重启.
- **启动时核对** (main.py 最先做, 在界面之前), 下面任何一条成立就判为非法:
  `foreign-seal` 封印解不开 (数据被复制到别的电脑 / 别的用户); `tampered-seal` 封印和记录对不上 (手改过序号); `rollback` 数据里的序号比锚点小 4 以上 (拿旧备份覆盖了);
  `other-epoch` 世代对不上 (不是这次安装的数据); `stripped` 数据里别的文件都在、连续性记录被删了而锚点还在; `anchor-tampered` 锚点被改坏; `pending` 其他设备发现了倒回去.
- **判为非法时**: 读出非法数据里的用户名, 清掉数据文件夹里的一切 (只留系统代理的备份 `sysproxy_backup.json`, 免得断网时还原不了), 弹出文本框 **"<用户名>,覆水难收."** (没有用户名时只有"覆水难收."),
  然后像第一次安装那样重新开始 (要重新填用户名, 重新开始配置期). 只清本机的数据: 不转告其他设备 (被搬走的副本和原来的设备共用同一份绑定, 不能连累原来的).
- **锚点投票**: 三个锚点里, 和数据一致的 (同一世代, 序号没有大得多, 没有 pending) 占多数时, 不一致的那个 (过时的, 别的权限写的, 被别的版本留下的) 不当证据, 通过时会被对齐;
  一致的不占多数 (例如只剩两个而且一对一) 才按下面的信号判.
- **日志**: 每次清数据的原因 (哪些信号, 哪个文件夹), 其他设备发现倒回去 (它们记着的序号 / 本机的序号), 数据文件被篡改 (哪个文件, 什么原因), 都记在 `%LOCALAPPDATA%\Obliphur\OIT\guard.log`
  (在数据文件夹以外, 清数据也删不掉; 超过 200 KB 换成 `.old`), 事后能查"为什么清了".
- **循环保护**: 清数据之后 10 分钟内, 下一次启动如果**只剩 `pending` 一个信号** (清数据之后程序自己又标记了, 或锚点还没对齐), 这次不再清, 数据以现在的为准并换一个新的世代 (`wipe.stamp` 记着上次清数据的时刻).
  清数据之后同一个进程里接着读数据文件不会被当成"被人删了" (内存里的密钥和索引在清数据时一起作废).
- **自己恢复备份会被当成倒回去**: 把旧备份复制回数据文件夹, 其他设备还记着旧世代里更大的序号, 同步时会发现 → 标记 → 下一次启动清掉. 要恢复自己的数据: 恢复后换一个新的世代
  (`Continuity.begin()`, 其他设备记着的是旧世代, 世代不同就不比序号), 锚点一起换掉.
- **不算非法**: 没有用过的数据 (新装); 升级到有这个功能的版本 (记录和锚点都还没有: 以现在的数据为起点); 重置 / 卸载 (锚点一起清掉, 世代换新); 数据文件夹是个符号链接 / 联接点 (放到别的盘, 只记日志).
  git 仓库里的开发版本不核对也不写锚点.
- **防复制**: 程序运行期间用独占方式打开数据文件夹里的 `.lock`, 资源管理器 / 备份软件复制整个文件夹时这个文件复制不了.
- 局限: 整盘镜像还原只能靠其他设备发现; 没有绑定其他设备时, 同时删光三处锚点再还原旧备份的人发现不了.

### 9.4 数据和设置的加密 (电脑)

数据文件夹顶层的 `.json` (设置, 记录, 名单, 合约, 同步的绑定, AI 配置 ……) 都是**加密 + 带校验**的信封, 不是明文 (`securefile.py`), 用记事本改不了:
- **格式**: `OITE1 | nonce(16) | 写入计数(8) | 密文 | HMAC-SHA256(32)`. 加密是 SHAKE-256(密钥‖nonce) 流密码 (标准库没有 AES), 先加密后校验, 校验的内容包括**文件名** (把一个文件的内容拷到另一个文件名下校验不过) 和计数.
- **密钥**: 32 字节随机数, 用 Windows **DPAPI** (绑定这台电脑 + 这个用户) 封着放在 `oit.key`; 数据拷到别的电脑 → 解不开 (配合 9.3 的连续性).
- **计数索引** `secure.idx` (也是信封) 记着每个文件最近一次写入的计数: 文件被换成旧版本 (计数变小 `rollback`) 或被删掉 (索引里有, 文件没了 `deleted`) 都能发现. 程序自己删文件走 `securefile.remove`, 不算.
- **篡改的处理**: 校验不过 `bad-mac` / 变成了明文 `plain` / 没有密钥 `no-key` / `rollback` / `deleted` / 索引坏了 → 这个文件按"不存在"读 (和损坏的文件一样用默认值), 并且在连续性的锚点里标记 pending, 立即重启;
  下一次启动时 (9.3) 清掉数据, 弹出 "<用户名>,覆水难收." 连续性记录里带着密钥的指纹, 密钥被删 / 被换也算非法 (`key-lost` / `key-changed`).
- **不加密的**: `sysproxy_backup.json` (断网时还原系统代理靠它, 密钥丢了也不能连累网络), `continuity.json` (自己有 DPAPI 封印), 日志 `.log`, 录像等非 json 文件, 子文件夹里的文件.
- **升级**: 第一次运行时生成密钥, 把现有的明文 `.json` 全部转成加密的; 此后再出现明文 `.json` 就是篡改. 重置之后 (数据文件夹被删光) 内存里的密钥作废, 留下的绑定先写明文, 下次启动再转成加密的.
- **联动程序 / 卸载程序**也用同一个密钥读 `sync_state.json` / `link_state.json` (同一个用户, 能解开); 联动程序读不到密钥时 (OIT 还没生成) 读明文.
- **设置 (config)**: 设置文件 `app_settings.json` 也在上面; 另外 `config_local.py` (能任意覆盖 `config.py` 里的数值) **只在开发版本里生效**, 公开发布版忽略它.
- **开发版本和装好的版本共用一个数据文件夹** (都是 `AppData\LocalLow\<程序名>`): 开发版本 (git 仓库里) 不生成密钥, 不核对连续性, 但数据文件夹里**已经有 `oit.key`** 时要用同一个密钥读写 (`securefile.configure`),
  否则它会把装好的版本加密过的 .json 当成乱码, 读成空数据, 存回去时把数据盖掉, 而且写进去的明文会被装好的版本当成篡改. 数据文件夹里还没有密钥时开发版本照旧写明文 (装好的版本下次启动时转成加密的).
  两个版本同时运行: 装好的那个启动时拿不到单实例互斥体 (3.5), 会弹出"已经有一个 OIT 在运行"再退出, 不再悄悄退出.
- **开发版本**不加密不核对 (除了上面那条), 方便调试; 手机上数据在应用的私有目录里, 没有 root 改不了, 不另加密.
- **局限**: 密钥在这台电脑的这个用户手里, 有本事的人可以自己调 DPAPI 解开再重写; 程序是 Python 源码, 能改代码的人什么都改得了. 防的是用记事本改 json, 拿旧备份覆盖, 删文件, 把数据搬走.

### 9.5 断电 / 崩溃不能引起清数据 (电脑)

写文件写到一半断电, 不能被 9.3 / 9.4 当成"数据被改过". 三层:
- **写得稳**: 所有写盘 (加密的 `.json`、`secure.idx`、`oit.key`、`continuity.json`、锚点文件) 都是"写 `xxx.tmp` → `fsync` → 改名" (Windows 用 `MOVEFILE_WRITE_THROUGH`), 先写数据文件、后写索引 (断电时文件的计数只会比索引大, 不会小),
  旧文件完好的话改名之前留一份上一次的 **`.bak`** (`continuity.durable_write`). 写临时文件再改名的老写法 (`xxx.json.tmp` 的内容也先 fsync) 一样.
- **读得宽**: 读到**半截的文件** (空的 / 全是 0 / 信封被截断或末尾补着 0) 时不记篡改: 先退回 `.bak` (计数最多比索引小 1), 没有 `.bak` 就当作空文件 (调用方本来就会处理损坏的文件). `secure.idx` 半截: 退回它的 `.bak`, 再不行按现有文件里的计数重建.
  `continuity.json` 半截: 退回它的 `.bak` (序号只差一次, 在 `TOL` 之内). `oit.key` 空的 / 半截: 用 `oit.key.bak`.
  **信封完整却校验不过**, 在一次正常结束之后, 仍然是篡改 (半截的文件不会"刚好长度完整").
- **运行标记**: 数据文件夹里的 `run.flag` 在程序运行期间存在, 正常退出 (主循环结束) 时删掉; 启动时它还在 = 上一次没有正常结束 (断电 / 崩溃 / 被结束), 日志 `guard.log` 里记一条 `UNCLEAN`. 这一次:
  读到坏的数据文件先退回 `.bak`; 少了最后一次写入 (计数比索引小 1) 不算倒回去; `continuity.json` 和它的 `.bak` 都没了, 锚点完好 (一致、没有 pending) 就从锚点重建记录, 不当作 `stripped`.
  `run.flag` 清数据时留着 (`KEEP`).
- **没有断电痕迹的照旧**: 正常结束之后文件被改坏 / 被删 / 被倒回去, 仍然按 9.3 / 9.4 清数据.
- 手机: 数据文件写完 `fsync` 再改名 (`Store.write`); 手机没有 9.3 / 9.4 的核对, 不会因此清数据.

### 9.6 系统时间被改

冷静期 (120 h)、设置的等待 (48 h)、每日额度、录像保留期 …… 都靠系统时间; 改系统时间就能躲开. 电脑 `clockguard.py`, 手机 `ClockGuard.kt` (装好的版本 / 封闭测试里生效, 开发版本不检测):
- **怎么发现**: 系统时间 − 开机以来的时间 (电脑 `QueryInterruptTime`, 手机 `elapsedRealtime`; 睡眠 / 休眠也算在里面, 不受改时间影响) = "开机的时刻", 同一次开机里不变. 它变了超过 **5 分钟** = 系统时间被改了 (5 分钟以内的调整, 例如自动对时, 不理; 小于 30 秒的漂移基准跟着走).
  睡眠 / 休眠不会误判 (两个量一起走). 程序没开着时改的: 重新打开时系统时间比上次记着的还早 (往回改) 才算, 往前改的分不清是不是"关机很久", 不管.
- **第一次发现**: 弹窗 "`<用户名>,这没有意义.你可以在10min内修改回来,否则你的数据会被清除.`" (电脑是只能手动关闭的提醒窗, 手机是提示), 开始 **10 分钟**倒计时 (只在程序运行时走). 状态存在数据文件夹的 `clock_guard.json` 里 (电脑上是加密的), 重启不丢.
- **改回来了** (开机时刻回到改之前的 5 分钟以内): 解除, 提示"系统时间已改回来". 程序重启过的同样判断; 重新开机过的按"现在的时间离改之前最后的时间有多远"估计 (改了 D: 离得比 D/2 近就算改回来了).
- **清数据**: ① 倒计时走完还没改回来; ② 倒计时里又改了一次 (改成别的时间, 不是改回原来的); ③ 警告过之后 **24 小时**内再发现被改 (哪怕上一次改回来了).
  电脑: 和 9.3 一样, 在锚点里标记 pending, 重启, 下一次启动清数据并弹出 "`<用户名>,覆水难收.`"; 手机: 只清本机 (和绑定的设备的绑定留着, 不转告它们), 清完弹出同样的文字. 只清本机, 不动别的设备.
- **局限**: 关掉 OIT (和联动程序) 之后改时间再打开, 往前改的发现不了; 能改程序代码的人什么都改得了.

### 9.7 源码被"非更新"的形式改动 (电脑)

OIT 是 Python 源码, 装在程序文件夹里. 直接改源码 (去掉限制, 绕开核对 ……) 而不是通过更新, 会清一次数据 (`srcguard.py`; git 仓库里的开发版本不检查):
- **程序文件** = 程序文件夹里的所有 `.py` / `.pyw` (跳过 `__pycache__`, `.git`, 安卓版, `closed_test` 等); 新增 / 删除 / 内容变了都算. **清单**: 每个文件的 SHA-256, 记在数据文件夹的 `source_manifest.json` 里 (9.4 的加密 + 校验: 改不了, 删不了, 倒不回去).
- **合法的改动只有两种**: ① 更新 (16): 覆盖完文件马上记下新的清单 (不管成功没有); ② 重新运行 `setup.exe` (装 / 修复): 解压完用 DPAPI 封一个"现在这些程序文件的指纹"令牌放在 `%LOCALAPPDATA%\Obliphur\OIT\src_update.dat`,
  OIT 下次启动时发现程序文件和清单对不上、但指纹和令牌一致 → 是安装, 接受, 记下新清单, 令牌作废.
  **1.0.375**: 1.0.374 的 `setup.exe` 重新安装会清数据 — PyInstaller 打的 exe 里没有 `secrets` / `hmac`, 在 exe 里 `import srcguard` → `continuity` 失败, 异常被吞掉, 令牌没发出, OIT 把这次安装当成源码被改过. 现在令牌由装好的那个 Python 子进程发 (有完整标准库, `setup.issue_source_token(dest, python)`), 发不出去才在 exe 里试, 都不行安装日志里写明 (`token_fail`); `release.py` 也给 PyInstaller 加了 `--hidden-import secrets/hmac`.
- **1.0.376 / 1.0.437 无代价解绑开关**: `devsync.UNBIND_FREE` / `SyncService.UNBIND_FREE` 为真时, 解除绑定没有冷静期 (已有的计划也算到期, 5 秒内解除), 解除后**不清空本机** (`app._check_unbind` / `Core` 不调 reset). 1.0.376 临时开过; 1.0.435 开成 true, **1.0.437 又改回 false** (恢复冷静期 120 小时, 到时清空操作解除的那台).
- **启动时** (数据核对之前) 对比: 对不上又没有令牌 → 数据核对多一个信号 `source-modified` (和数据被搬走一样): 有用过的数据就清, 弹出 "`<用户名>,覆水难收.`", `guard.log` 里记哪些文件变了.
  清完以现在的源码为新的基准 —— **清一次**, 不是每次启动都清. 清单文件在却读不出来 / 被删 (索引里有) 也当作被改过.
- **运行中**每 5 分钟对比内存里的清单; 对不上 (隔 20 秒再看一次还对不上; 正在更新时不报) → 在锚点里标记 pending, 立即重启, 下一次启动清数据.
- **第一次运行** (没有清单: 升级到有这个功能的版本 / 清过数据 / 重置之后) 以现在的程序文件为起点, 不当作改动.
- **自己动手装的新版本** (不用 setup.exe, 直接把压缩包解压覆盖) 算"非更新", 会清一次数据; 请用 OIT 里的更新或 setup.exe.
- **局限**: 源码是明文的, 能改源码的人可以同时改掉这个检查 (或者改完再删掉清单对应的数据以外的一切) —— 这里防的是随手改一两个文件; 联动程序不做这个检查 (它改写锚点会被运行着的 OIT 的下一次推进盖掉).
